# Experiment 028 program ledger

This is the one place where no learning from experiment 028 gets lost. It collects every candidate, fact, dead end, open hypothesis, blocker and lane assignment from the lane logs (lanes/*.md), the 21:20Z review (review-20260924T2120Z.md), the research set (research/2026-09-25-metal-native-design.md, -design-review.md, -api-check.md, -playbook.md, 2026-09-24-metal-2x-workloads.md), the m2 results (m2/results/) and git (branches ultra/*, cand/*, probe/* in the hipdelta-gbsa repository). The lead is the only writer.

As of 2026-09-24 22:00Z, with every later lane-log entry up to 22:26Z folded in by the audit and marked with its time (pme 22:10Z and 22:15Z, mixed 22:08Z to 22:25Z, dispatch 22:14Z to 22:25Z, atomics 22:05Z to 22:26Z, profiler 22:09Z to 22:25Z, infra 22:10Z to 22:25Z), plus branch refs read from git during the audit. Base commit is 6df2b8bcb. The M3 Ultra is the target, the M2 (8 GB) must not regress, and OpenCL single on the same M3 Ultra is the denominator (ultra-base's OpenCL, from a dedicated window).

The measurement rule: every number taken on the shared Studio is a screen, never a result. Only numbers from a dedicated window (3 rounds of 30 s, no builds, no other lane's GPU work, run by the lead and infra) count as results. As of 22:00Z no dedicated window has run in 028, so every 028 number in this file is a screen. The only confirmed M3 Ultra numbers are lab 025's dedicated baselines. The owner's estimate is that shared-Studio absolute ns/day reads about 80 to 90% of a dedicated run, and that interleaved A/B ratios hold up better.

Conventions. "Screen" means shared machine. Clocks: host clock is benchmark.py's datetime.now() around step() (or perf_counter in lab scripts); counters mode is the profiler's stage-boundary GPU timestamps with one encoder per dispatch; buffers mode is GPUStartTime/GPUEndTime per command buffer; forcetime is host wall time over force evaluations. Precision is single unless marked mixed. Ratios are candidate over ultra-base in ns/day (higher is better) unless marked otherwise. Commit times in git are local (+03:00); lane times are Z.

## 2. Established facts

Every fact below is a screen unless it cites lab 025 or an earlier dedicated lab. "Counters" means counters mode, GPU timestamps, single, 6df2b8bcb, shared Studio.

### Hardware and Metal API

- No 64-bit atomic add on any Apple GPU. MSL 4.1 section 6.16.4.6: atomic_ulong has only atomic_max/min_explicit, relaxed, device, void return. atomic_fetch_add_explicit on device atomic_ulong fails to compile on the M3 Ultra (Apple9). The Feature Set Tables footnote 7 ("full set of 64-bit atomics on Apple9") is misleading. Sources: lanes/atomics.md 19:30Z; research api-check items 12, 15.
- The M2 (Apple8) has no float atomic opcode; atomic_float add is a CAS loop (lab 004: 190.8 ms on M2 vs 0.34 ms on the Ultra). Device atomic_float is Metal 3; threadgroup atomic_float add is MSL 4.1 only, needs macOS 27 and LanguageVersion4_1; the platform compiles at 3.2. Sources: playbook section 1; api-check item 4; MetalContext.cpp:482-485.
- Atomics microbenchmark (ub.mm, 288k tiles, 55M adds, M3 Ultra, GPU): emulated 64-bit add 1480 us (37 G adds/s), one non-returning 32-bit atomic 880 us (62.5 G/s), plain RMW 220 us (250 G/s). Batched low words and deferred carry equal the emulation; with 400 FMAs per tile 2630 / 2596 / 2490 / 2430 us. The limit is atomic op count, not latency. Source: lanes/atomics.md 19:30Z.
- Split-word fixed-point atomic add (common.metal:57-67) is exact under contention (lab 004); integer adds commute bit for bit. Source: design doc dispatch design 3.
- Measured working sets: M3 Ultra recommendedMaxWorkingSetSize 83494174720 B (77.76 GiB), maxBufferLength 62620631040 B (58.32 GiB); M2 5726633984 B. OpenCL CL_DEVICE_MAX_MEM_ALLOC_SIZE 15655157760 B = Metal maxBufferLength/4, CL_DEVICE_GLOBAL_MEM_SIZE 83494174720. Sources: lanes/dispatch.md 21:44Z; lanes/workloads.md item 2.
- Compile settings: LanguageVersion3_2, MathModeSafe, MathFloatingPointFunctionsPrecise (MetalContext.cpp:482-485). Pipelines built without a descriptor (MetalContext.cpp:505): no label, maxTotalThreadsPerThreadgroup 0. __launch_bounds__ empty (common.metal:16). __syncthreads = threadgroup_barrier(mem_threadgroup | mem_device). No buffer is declared coherent. Source: playbook sections 1-5.
- Every MetalArray is MTLStorageModeShared with tracked hazards (MetalArray.cpp:53-55); one serial compute encoder per command buffer; copyTo is a blit (MetalArray.cpp:99-101), used by the short-list sort every step. Source: design doc dispatch; playbook section 2.
- Launch geometry: force kernels use 10*4*cores blocks of 64 (2560 threads/core, 2400x64 on 60 cores); executeKernel caps everything else at 12*cores blocks of 64 = 720x64 = 46080 threads (768/core, below Apple's 1K to 2K per core), tuned on the M2 in 24c34d794. GB, bonded, spread, interp, integration, RNG all run at 720x64 on large systems. The playbook's "GBSA runs 2560 per core" is wrong: executeKernel clips GBSA to 720 groups. Sources: playbook report 2; lanes/profiler.md 21:46Z; design doc pair kernels.
- Share of step time in kernels at the 720-group cap: gbsa 35.2%, apoa1rf 21.0%, apoa1pme 48.5%, apoa1ljpme 53.4%, cellulose 52.1%, stmv 53.7%, rf 1.8%, pme 4.1%, dhfr 4.3%. computeBondedForces runs 720x64 on apoa1, cellulose and stmv, 543x64 on pme and dhfr, 115x64 on gbsa and rf. Source: lanes/profiler.md.
- Pipeline limits (pipestat.sh, 22:03Z): all 24 computeNonbonded variants (gbsa, pme/rf, apoa1 sizes, 64 or 256 threads, unroll 1/2/4, TGP/TGF/TGA) report maxTotalThreadsPerThreadgroup 1024; registers never cap threadgroup size. Threadgroup memory: TGP+TGA 1792 B, TGP+TGF+TGA 2816 to 3840 B. Source: lanes/nonbonded.md 22:03Z.
- metal-cpp API facts (vendored at 6df2b8bcb): indirect dispatch exists, zero-threadgroup {0,1,1} behavior undocumented; encodeSignalEvent legal only between passes; up to 64 uncompleted command buffers per queue; MTL4CommandQueue has no hazard tracking; ICB compute commands have no setBytes and only concurrent dispatch. Source: api-check items 1-11.
- MSL memory model: device memory is threadgroup-coherent only by default; cross-threadgroup visibility needs coherent(device) or atomics; no forward-progress guarantee between threadgroups (5.2.3.6). fetch-and-modify atomics are relaxed-only even in 4.1. Sources: playbook section 1 table and myth 2. Unresolved conflict: api-check item 4 says per-op acquire/release orders exist from MSL 4.1 (api-check has 17 items, so the old citation of item 20 was wrong).
- Fast-math bounds (MSL Table 8.2): fast rsqrt <= 2 ulp, 1.0/x <= 1 ulp, x/y <= 2.5 ulp, fast exp <= 3+floor(|2x|) ulp; precise sqrt correctly rounded. Source: api-check item 14.

Ultra estimates (unmeasured): about 21 TFLOPS FP32, 650 to 740 GB/s, about 15k threads to fill 60 cores; Mesa sets a coherency bit on atomics for multi-die parts. Source: playbook report 4.

The honest statement on 4x. 4x Metal over OpenCL single on benchmark.py is not reachable. Both platforms run on the same GPU, and after the atomic tax the step is pair math, FFT and list build, which OpenCL's compiled shared kernels already run at similar efficiency. 4x would mean removing about 75% of the GPU work OpenCL does. The measured free-atomics bound caps accumulation redesigns at 1.19 (rf) to 1.80 (apoa1pme) per force evaluation. Nothing in either table reaches 2x in single, and mixed stays near or below 1.7. The two routes to a bigger number are outside the benchmark contract: changing the computation (grid, cutoff, FP16, multiple time stepping), which the Reference gate forbids; or changing the metric.

Aggregate throughput is the metric route. Several simulations sharing the 60-core GPU could raise total ns/day, because small systems like gbsa leave most cores idle. research/2026-09-24-metal-2x-workloads.md item 7 found no structural difference between the platforms (OpenCL gives each process its own queue with no global lock) and expects 1.0 to 1.1x Metal over OpenCL, since both fill each other's gaps. So aggregate throughput may raise absolute ns/day for users running many jobs, but it is unlikely to raise the Metal/OpenCL ratio. workloads is measuring it (1, 2, 4, 8 concurrent gbsa processes per platform); no number is logged yet. The workloads doc's one confident 2x+ class is mixed precision, where OpenCL refuses to run and users fall back to the CPU (M2 GPU 6 to 7.5x the CPU in lab 001); that is workloads item 1, also in progress.

### Which barrier orders what volatile covered in amoebaGk.cc (636ea574f)

Metal's SYNC_WARPS is `simdgroup_barrier(mem_flags::mem_threadgroup)` (platforms/metal/src/kernels/common.metal:38), a real barrier and a compiler fence for threadgroup memory.

ATOM2_ARG_SPEC (amoebaGk.cc:349-352) qualified the by-value AtomData2 parameter of computeOneInteractionF1, F2, T1, T2 and B1B2 (declared at :354-358, called only from computeGKForces). It never covered a threadgroup access. The argument is copied from `localData[tbx+j]`, which is declared without volatile, so the read that builds the copy was an ordinary threadgroup load before and after the change. The qualifier only kept the callee's private copy in memory, which is where the 3x went. The accesses that feed those calls are ordered as follows:
- Diagonal tile: the fill at :418-429 is ordered by :430 before the F1/F2 reads at :439-440. :445 orders them before T1/T2 at :459-460, and :464 orders those before B1B2 at :477. No lane writes localData inside those loops except :479. There, all 32 lanes add to the same entry's bornForce at once. That value is never read (B1B2 doesn't read atom2.bornForce, and :483 uses data.bornForce), so it's a harmless upstream race. The :480 barrier sits inside `atom1 < NUM_ATOMS`, so lanes past the end skip it. That's undefined in Metal, but only in the last, partial diagonal tile, and no tile follows it in a no-cutoff sweep.
- Off-diagonal tile: the fill at :489-491 is ordered by :492. In the force loop each lane reads entry tbx+tj at :499-500 and subtracts from that entry's force at :502. A different lane reads the entry in the next iteration, after :506. The torque loop works the same way (reads :532-536, write :537, barrier :540, fill barrier :527), and so does the Born loop (read :564, write :566, barrier :569, fill barrier :559). No callee reads force or bornForce.

ATOM2_PTR_ARG_SPEC (amoebaGk.cc:869-873) qualified the `LOCAL_ARG AtomData4*` of computeOneEDiffInteractionF1, T1 and T3 (:875-877, called only from computeEDiffForce). Here volatile did turn each field read through the pointer into a threadgroup load. Ordering now:
- Cutoff path, diagonal: fill, then :968, F1 reads :976, :981, T1 reads :996, :1004. No localData writes inside these loops.
- Cutoff path, off-diagonal: fill :1010-1011, then :1012 and :1017. F1 reads entry tbx+tj at :1025, the same lane writes its force at :1028, and :1031 hands the entry to the next lane. Torque: own-entry reset :1047, :1048, T1/T3 reads :1055/:1057, write :1058, :1061. The tile ends at :1073.
- No-cutoff path (amoebagk uses this one): :1100 opens each tile, and the fill at :1123-1126 is ordered by :1127. F1 read :1137, write :1140, :1143. Own-entry reset :1159, :1160, T1/T3 :1165/:1167, write :1168, :1171. The next tile's fill waits for :1100.
F1, T1 and T3 read positions, multipoles, induced dipoles, damping and thole, never force. Every entry a lane reads was last written by a lane before a barrier that every lane of the SIMD group reaches. The fresh-context review traced the same map independently.

### volatile sweep of the plugin kernels

The AMOEBA plugin has no other volatile parameter. Its other hits are the skipTiles arrays of the no-cutoff tile walk: multipoleFixedField.cc:611, multipoleElectrostatics.cc:512, pmeMultipoleElectrostatics.cc:579, multipoleInducedField.cc:501, amoebaGk.cc:1084, hippoComputeField.cc:204 and hippoNonbonded.cc:262. All seven have the same structure (pmeMultipoleElectrostatics.cc:600-615): the reads at :601, :613 and :615 follow the writes at :605 and :608 across :611, and :600 and :602 keep the next round's writes behind this round's reads. So volatile is redundant there on Metal too, but the array is read only a few times per tile, so I expect little speed from it. Drude and RPMD have no volatile. hippoNonbonded.cc:40 and :48 are CUDA inline asm and never reach Metal.

When removing volatile is safe on Metal, as I read it:
1. volatile on a by-value parameter or any thread-space local never protected shared data, so removing it is always safe. It can cost a lot: it forces a stack copy in the hottest loop.
2. volatile on threadgroup memory is redundant when every cross-lane read follows the write across a SYNC_WARPS or SYNC_THREADS that the whole SIMD group reaches. Both are compiler fences for threadgroup memory on Metal. customNonbondedGroups.cc:155-156 qualifies: anyInteraction is written at :186 between the :176 and :189 barriers and read at :175 and :191, and tileIndex is written at :194 and read at :196 across :195.
3. Removing it is unsafe where code relies on lockstep with no barrier between the write and the read, the classic warp-synchronous reduction. Metal promises no lockstep, so such code is already wrong there, and volatile doesn't fix it. The common reduceValue helpers I checked (rmsd.cc:7) put a barrier after every step, so they're rule 2.
4. A barrier under divergent control flow (amoebaGk.cc:480) is undefined in Metal whatever the qualifier. Look for those separately.
The size of the win depends on how often the hot loop touches the volatile data. A by-value struct passed per pair is huge; a flag or skip index read a few times per tile is small.

- Side note for the core lanes: in single precision Metal maps EXP and RSQRT to fast::exp and fast::rsqrt unconditionally. OpenCL measures the native functions on the device and uses them only below 1e-6 error. That may explain the AMOEBA GK villin miss on the M3 Ultra only (1.19e-5 against 1e-5). Untested.

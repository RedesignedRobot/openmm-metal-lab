# Native Metal playbook for OpenMM's hot kernels

Research lane, 2026-09-25. Target: M3 Ultra (Apple9, 60 GPU cores, macOS 27.2, Xcode-beta 27.2, Metal 32023.922). Must not regress: M2 mini (Apple8, 8 GB). Base: `metal-hipdelta-gbsa` at 6df2b8bcb.

This playbook adds to `research/2026-09-24-apple-gpu-metal-brief.md` and does not repeat it. It leaves out lab 008 dispatch costs, lab 004 and 011 atomics numbers, df64 error bounds, math-mode pragmas and the MTL4 timestamp recipe. Read the brief for those.

Each claim carries one tier:
- official: Apple states it.
- lab: one of our experiments measured it.
- third-party: someone outside Apple measured it.
- RE: reverse-engineered by Asahi, dougallj or Mesa.
- inferred: my own reasoning.

Nothing here was built or run. I re-read the worktree lines that decide the conflicts between the five source reports and cite them as "verified".

## If a lane does only five things

1. Fix computeRange. It runs as one 256-thread threadgroup over every atom (`MetalSort.cpp:65`, `rangeKernelBlocks = 1`, verified). On apoa1ljpme it runs twice per step. It lives in the PME atom sort, not the neighbor-list block sort. This is the largest single item measured (250 us per step).
2. Get overlap from pass structure, not from untracked buffers. Every OpenMM buffer is hazard-tracked (`MetalArray.cpp:55`), and tracking delays a command only when it conflicts with a write to the same resource, so passes without a write conflict already overlap. A concurrent encoder needs memoryBarrier calls whatever the tracking mode. None of the brief's concurrency levers needs untracked buffers first (research/2026-09-25-ledger-questions.md, section 2).
3. Remove the blit encoder switches from the step. The short-list sort calls `buckets.copyTo(cudata)` every step (`MetalSort.cpp:106-107`, verified), and that goes through a blit encoder.
4. Build pipelines from a `MTLComputePipelineDescriptor` that sets a label, and map `__launch_bounds__` to `[[max_total_threads_per_threadgroup(N)]]`. Do not turn on `threadGroupSizeIsMultipleOfThreadExecutionWidth` globally (see myth 9).
5. Before any rewrite, profile headless with `gpucapture` plus `gpudebug profile run`. Both ship in `/usr/bin` on macOS 27 (verified on this machine), and profiling works on M3.

Current launch geometry, verified in the worktree. Size the levers against this.

- Nonbonded and GBSA use `numForceThreadBlocks = 10*4*cores` blocks of 64 threads (`MetalNonbondedUtilities.cpp:60-61`; `CommonKernels.cpp:2100-2102`). That is 2560 threads per core, already above Apple's floor.
- `executeKernel` caps grids at `numThreadBlocks = 12*cores` (`MetalContext.cpp:158,172,590`). With 64-thread blocks that is 768 threads per core, below Apple's 1K floor. Bonded, integration and most utility kernels launch through this path.
- findBlocksWithInteractions runs 32-thread threadgroups, one SIMD group each. `AMD_RDNA` is defined when simdWidth is 32 (`MetalContext.cpp:175-176`), so the kernel uses warpSize 32 and syncs with `SYNC_WARPS` (simdgroup_barrier), not `__syncthreads`.
- The nonbonded tile rotation is `simd_shuffle_rotate_down(x, 1)` (`intrinsics.metal:23-25`). That is the 2-cycle uniform-delta path, not the 32-cycle per-lane path.

What this means for design, all inferred:
- On M3 the register cliff mostly disappears. Occupancy now falls when a kernel touches too much threadgroup, stack and buffer data.
- Mixing integer work into FP32 loops costs more than it did on M1.
- Device atomics cost more on the two-die Ultra than on one die.
- On M2 the 52-register budget still decides occupancy, and float atomics are CAS loops.

## 2. Levers by OpenMM hot kernel

Levers are ranked by expected payoff within each kernel. "M2" gives the Apple8 fallback.

### Neighbor list: findBlocksWithInteractions, sorts, computeRange

1. **computeRange as a real reduction.**
   - Where it lives: the PME atom sort, which is uniform (`CommonCalcNonbondedForce.cpp:464`). It runs every step above 15,000 atoms (`:980`) and a second time for LJPME dispersion. The block sort is non-uniform, and there computeRange only clears bucket counters (`sort.metal`, `#if UNIFORM`).
   - The cause is launch geometry: one threadgroup of 256 threads (`MetalSort.cpp:61-65`, verified), where HIP launches `ceil(n/256)` groups (`HipSort.cpp:66`). One threadgroup uses one of 60 cores.
   - Options, cheapest first:
     - (a) Skip the min/max scan. The key is a grid index, so its range is `[0, gx*gy*gz)`. Keep the bucket-counter clear, and check that bucket occupancy stays balanced.
     - (b) An MLX two-pass all-reduce: about 2x-cores threadgroups each do `simd_min`/`simd_max`, then threadgroup memory, then a 32-thread second pass. It needs no coherence qualifier and no counter.
     - (c) One pass with relaxed `atomic_fetch_min/max` on `uint`. PME keys are non-negative ints, so no float encoding is needed. The range buffer must be reset each step.
   - Do not build a multi-block "last block reduces" version without `coherent(device)` on `range[]`. The current code is correct only because it runs one block.
   - Evidence: official for MSL 4.8 and simd reductions (Apple7+); MLX `reduce.cpp:330-405`.
   - Expected gain: from 250 us to tens of us per sort (inferred).
   - M2: identical code.
2. **Block sort without O(n²) or a blit.**
   - `sortShortList2` stages keys in threadgroup memory and has each thread count smaller keys across the whole list, then `buckets.copyTo(cudata)` switches to a blit encoder (`sort.metal:53-71`, `MetalSort.cpp:106-107`, verified).
   - The sort key is `(bin << BIN_SHIFT) + blockIndex` with 20 bins (report 3, `findInteractingBlocks.metal:126-141`). The keys are unique and bin-major, so a stable counting sort on the bin alone gives the same order.
   - Counting sort design:
     - One threadgroup of up to 1024 threads.
     - `simd_ballot` plus popcount gives each lane's rank per bin inside its SIMD group.
     - A `simd_prefix_exclusive_sum` over per-SIMD counts goes through threadgroup memory.
     - Each thread scatters into the output array directly.
     - Loop over chunks when there are more than 1024 blocks (apoa1 has 2882, stmv about 33k).
   - Separately, try the Apple9 advice from 111373 (11:43-12:46). When every thread reads the same staged element, reading device memory directly or broadcasting with `simd_shuffle` may beat threadgroup staging.
   - Expected gain: most of the 48.5 us per step, if that time is kernel plus encoder switch. Open question 5 checks that split.
   - M2: identical. Ballot is Apple6+.
3. **Skip neighbor-list work on reuse steps.**
   - findBlockBounds, computeSortKeys, the block sort and sortBoxData run every step (`MetalNonbondedUtilities.cpp:416-423`, verified). The rebuild flag is computed afterwards in sortBoxData, and findBlocksWithInteractions returns early when it is 0 (`findInteractingBlocks.metal:306`, verified).
   - Fix: compute the displacement flag first, in findBlockBounds or a tiny kernel. Then either early-exit the sort kernels or drive them with `dispatchThreadgroups(indirectBuffer:...)`, writing zero threadgroups on reuse steps (FST Apple3+, official).
   - Risk: check whether nonbonded reads sortBoxData outputs on reuse steps. CUDA has the same ordering, so this is an OpenMM-wide pattern, not a Metal bug.
   - M2: identical.
4. **computeBucketPositions as a SIMD scan.**
   - Today it is a Hillis-Steele scan in one 1024-thread group with 2 barriers per level, about 20 barriers per 1024 buckets (`sort.metal:241-269`).
   - MLX `scan.h:247-401` does a serial per-thread scan, then `simd_prefix_exclusive_sum`, SIMD totals through threadgroup memory, and a second SIMD scan. That is about 4 barriers per 4096 elements.
   - It is also the building block for the counting sort in lever 2. Official Apple7+.
5. **Aggregate bucket atomics.**
   - `assignElementsToBuckets` does one device `atomicAdd` per element.
   - Count per bucket in threadgroup atomics, then publish one device atomic per bucket per threadgroup (10580, 10159 official; applegpu RE). Ballot plus one lane does the same for `interactionCount` wherever a whole SIMD group appends.
   - Do not rely on Apple's compiler to do this for you. Mesa does it (`nir_opt_uniform_atomics`), and Apple does not document whether its compiler does.
6. **findBlocksWithInteractions itself.**
   - It is already SIMD-native: ballot and popcount compaction (`findInteractingBlocks.metal:455-460`, verified) and simdgroup barriers.
   - Remaining levers:
     - Put the `[[max_total_threads_per_threadgroup(32)]]` hint on it. Its `__launch_bounds__(GROUP_SIZE)` is thrown away today.
     - Try Turner's half-precision `|a|²+|b|²-2a·b` distance test. It cut 39% on M1 Max, but against a threadgroup-prefix baseline OpenMM no longer has, and it needs a padded-cutoff correctness check (third-party).
     - Look at tile-list locality. Apple's Cycles case gained 10 to 30% by partitioning before sorting (10159).
   - M2: the same. The register hint matters more there.

Not worth a lane: ray-tracing neighbor search. On Apple9, box-against-box block tests need custom intersection functions on the shader cores. The intersection-query API from compute turns off the reorder stage (111375). RT loses to cell lists at 1 nm cutoffs with hundreds of neighbors (ORCS, arXiv 2601.15633; RTNN results exclude BVH build). M1 and M2 have no RT hardware.

### Nonbonded and GBSA pair tiles

1. **Register budget hints.**
   - Map `#define __launch_bounds__(x)` (`common.metal:16`) to `[[max_total_threads_per_threadgroup(x)]]`. computeNonbonded, findBlocksWithInteractions and computeBucketPositions already declare it (verified).
   - The GBSA tile kernels in `common/src/kernels` declare nothing, so give them the hint through a pipeline descriptor with `maxTotalThreadsPerThreadgroup = 64`.
   - Apple says the hint lets the compiler plan registers and spills. Pick the smallest multiple of the width that works (10580 at 19:45; official). MLX puts it on its sort kernels.
   - Attribute placement differs between `extern "C" __launch_bounds__ __global__` and `__global__ __launch_bounds__`, so run a compile test.
   - Largest expected effect on M2, where the cliff exists.
2. **Cut integer work in the inner loop.**
   - Apple9 co-issues FP and INT poorly (leman).
   - On M1/M2, IMUL costs 4 FMAs, and rsqrt next to IMUL serializes: 12.9 cycles (metal-benchmarks).
   - Precompute exclusion masks and index strides outside the j loop. Use signed `int` indices so loads vectorize (10580 at 15:22, official). `gbsaObc.cc` has 48 `unsigned int` uses, many of them array indices.
3. **Division and rsqrt precision per call.**
   - Precise divide costs 5x fast on M1/M2 (metal-benchmarks).
   - Use `metal::fast::` per call in single-precision tile math, where the forces gate allows. Keep `precise::` and safe math in df64.
   - Open question 7 is the check that `/` really lowers to the slow path under `MathModeSafe`.
4. **Occupancy on Apple9 is about touched memory.**
   - Shrink threadgroup staging in the GBSA tiles, and in any nonbonded exclusion staging, then compare against the Occupancy Manager Target and L1 eviction counters (111374).
   - Apple says threadgroup memory used as a cache of device data may lose on M3 (111373).
5. **Pre-reduce before atomics.**
   - The nonbonded kernel already sums per atom per tile (brief).
   - Check that the GBSA Born-sum and chain-rule kernels do the same. Where they don't, use `simd_sum`, or a shuffle tree for 64-bit fixed point, since `simd_sum` has no 64-bit form. Bit-cast long to uint2 and shuffle that (MLX `utils.h:383-449`; OpenMM already has `simd_shuffle(long)` in `intrinsics.metal:7-13`, so add `shuffle_down` and `shuffle_xor` overloads).
   - Fewer device atomics matter most on the two-die Ultra (inferred).
6. **Try a 32-thread threadgroup variant.**
   - At 64 threads the tile kernels run two SIMD groups and need threadgroup barriers. At 32, `simdgroup_barrier` is enough (10631).
   - This is a real A/B. It changes grid count, so also re-sweep `numForceThreadBlocks`.
7. **`uniform<T>` on loop bounds and flags from `setBytes`** (MSL 2.14). Cheap to try, gain unmeasured.
8. **Skip:** simdgroup_matrix and tensor ops. On M4 Max, Metal 4.1 tensor matmul beat simdgroup_matrix by only 1.05 to 1.21x at fp16 (Rigel, third-party), and pair tiles are bound by gathers and transcendentals. M5 speedups apply to fp16, bf16 and int only (111432).

M2: all of the above is Apple7+ except `simd_shuffle_and_fill` (Apple8+, fine). Check each tile pipeline's `maxTotalThreadsPerThreadgroup` on the M2 at load time, and fall back to the current path if it reports less than the launch size.

### PME: spread, sort, FFT, interpolate

1. **Float-atomic spread on Apple9** is the brief's lever 1; nothing new here. The new evidence is that the ISA confirms the M2 CAS loop (RE), so keep fixed point on Apple8 for a reason, not a guess.
2. **Two-level spread.**
   - Accumulate a brick in threadgroup memory, then flush once per threadgroup. On Apple9 use MSL 4.1 threadgroup `atomic_float` add. That needs `LanguageVersion4_1` and macOS 27, and the platform compiles at 3.2 today (`MetalContext.cpp:483`, verified).
   - Where one SIMD group's lanes hit the same point, `simd_sum` first (MLX custom-kernel docs). The atom sort already orders atoms by cell.
   - For a hot point, spread atomics over privatized sub-counters (Turner's molecular-renderer uses 8 per voxel).
   - M2 fallback, inferred and risky: a 32-bit fixed-point brick with threadgroup `atomic_int`, which is fast on Apple7+. It avoids the CAS loop but needs an overflow analysis for the brick scale. If that fails, stay on the current split 64-bit path.
3. **The PME atom sort** carries the computeRange fix above, plus the scan fix.
   - Longer term, replace the five-dispatch bucket sort with a counting sort over grid cells. Spreading needs locality, not a total order (inferred).
   - Morton-order the cells if the MMU limiter is high (111432 traversal idea, inferred transfer).
4. **FFT stays VkFFT.**
   - The vendored 1.2.33 caps Metal threadgroups at 256 threads for DCT-IV only (`vkFFT.h` about line 39866; unchanged at upstream 066a17c). It compiles with fast math (`:35664`, `:38936`).
   - Try `aimThreads` and `registerBoost` overrides, and dump the generated MSL with `keepShaderCode` for the ISA workflow in section 4.
   - The brief bounds the gain at about 4% of apoa1pme. MLX FFT is 1D Stockham with per-axis copies and `fast::cos` twiddles, so it is not a better base.
5. **Interpolate:** fp16 B-spline weights only if the PME error budget allows. Conversions are free on Apple9 (111373), but this is low priority.

M2: fixed-point spread, the same sort fixes, VkFFT unchanged.

### Bonded (computeBondedForces)

1. **Grid size.**
   - It launches through the `executeKernel` cap: 12 blocks per core times 64 threads, which is 768 threads per core (verified). That is below Apple's 1K to 2K per core, and 24c34d794 tuned the 12 on the M2.
   - Sweep 16, 24 and 32 on the Ultra and keep 12 on Apple8. The multiplier also moves the integration kernels, so gate the change per family and sweep both.
2. **Per-atom force atomics.** Where terms are ordered so that neighboring lanes share an atom, pre-reduce with shuffles before the split 64-bit add (10159 pattern). Without that order, the gain is small (inferred).
3. **Kernel hygiene** (10580, 10632, 111373, official):
   - Use signed loop indices.
   - Pass parameters as one `constant` struct, which is preloaded into uniform registers.
   - Keep dynamically indexed stack arrays out of the concatenated bonded kernel.
4. **Transcendentals.** `acos`, `sin` and `cos` are precise today (brief). The fast versions are about 1.7x cheaper on M1/M2 (metal-benchmarks). Gate on the forces test.

M2: identical code. Keep the M2 multiplier.

### Integration and constraints, df64 in mixed

1. **Fuse the chain.** The Langevin, SHAKE, SETTLE and position-update kernels (about 50 us per step) should become fewer dispatches (WWDC25 205 at 16:30, official). Every serial boundary is a coherency flush (10153) plus about 1.9 us (lab 008).
2. **Treat the work as latency-bound.**
   - A few thousand waters fill few SIMD groups on 60 cores, and dependent chains then run up to 5x slower per instruction (metal-benchmarks).
   - Give each thread two to four independent molecules to add ILP. Do not simply enlarge threadgroups.
   - Short dispatches also drop the clock (Turner).
3. **Restructure df64 cost.**
   - df64 add is 11 fp32 instructions, multiply 7 and divide 29 (metal-float64).
   - Use one df64 reciprocal per molecule and reuse it, not repeated df64 divides or sqrts.
   - The oxDNA native Metal backend reports its df64 "mixed" tier at 5 to 15% over float (third-party, M4 Air, which is Apple9, not Apple10 as the report said).
   - Keep constraint math inside the mixed-precision contract in `research/2026-09-23-mixed-without-fp64.md`. Do not demote it to fp32 without that review.
4. **Constants in double from the host** as hi/lo float pairs. MLX computes Bluestein constants in double on the CPU for the same reason (`fft.cpp:323-350`).
5. **Denormal flush** (MSL 8.1). The lo word of a df64 pair can flush near zero. Test tiny constraint corrections explicitly.

M2: identical code. The brief's (hi, lo) storage lever applies to both families.

### Per-step orchestration

1. **Tracked buffers, split passes, and barriers inside concurrent encoders.**
   - Keep buffers tracked. Tracking delays a command only when it conflicts with a write to the same tracked resource (MTLHazardTrackingMode.tracked, official). Passes without a write conflict already overlap: the PME chain starts while the list build still runs, across a command-buffer boundary, though both read posq (experiments/028-ultra-max/lanes/pme.md 22:35Z, lab).
   - Inside a concurrent encoder, tracking neither serializes nor protects: "If you encode multiple commands that access a single resource, you're responsible for synchronizing the memory operations to that resource" (MTLDispatchType.concurrent, official). dispatch's probe 1 ran a concurrent encoder over tracked buffers with no barriers and got rel|dF| 0.83 to 0.85 and a GPU page fault (lab). Only memoryBarrier calls make it correct.
   - A serial encoder runs dispatches in order and ignores memoryBarrier (`MTLComputeCommandEncoder.h:317`, `:324`, official), so untracked buffers change nothing inside one.
   - MLX's barrier logic is the template for a concurrent encoder. It opens `computeCommandEncoder(DispatchTypeConcurrent)` (`device.cpp:580`), records per-encoder input and output sets, and inserts `memoryBarrier(BarrierScopeBuffers)` only on read-after-write or write-after-read (`device.cpp:335-500`). Its untracked allocation (`allocator.cpp:16`) is optional here.
   - Untracked buffers would remove whole-resource false dependencies between passes (Apple tracks per resource, and pmeForce exists to dodge this on forceBuffers). No planned lever needs that.
   - Force kernels that only add through atomics need no barrier between them (Apple resource-synchronization doc: atomic accesses need no synchronization).
   - Check for aliased sub-buffers before relying on buffer identity.
   - Official for the API; MLX is the production template.
2. **No blits inside a step.** Replace `MetalArray::copyTo` with a compute copy kernel. It runs in the sort short-list path every step, in `IntegrationUtilities.cpp:952-1029` and in the barostat save. Or swap the argument pointers. MLX has no blit encoder at all.
3. **Unretained command buffers** (`commandBufferWithUnretainedReferences`). OpenMM buffers live as long as the context. MLX does this (`device.cpp:323,559`).
4. **Residency set on the queue, as a cheap trial.** Apple says residency resolved at commit can delay GPU start. MLX comments "Metal locks a command buffer's residency at commit time" (`device.cpp:517`). Open question 9 measures it.
5. **Second PME queue joined with a classic `MTLFence`**, not events. Fences work across queues on one device if the updating command buffer commits first (mtlfence doc, official). Never update and then wait on the same fence in one pass: it can deadlock.
   - Turner measured only about 2x concurrency across queues, against up to 96 commands inside one encoder. Overlap inside the main encoder is the bigger lever.
6. **Barrier granularity.** Apple does not say whether `memoryBarrier(resources:)` is scoped to the listed resources. Assume it drains the encoder, and group independent kernels before one barrier.
   - Classic encoders gained `barrier(afterQueueStages:beforeStages:)` in macOS 26.
7. **Fences in kernels.**
   - `__threadfence` is a seq_cst device fence (`common.metal:15`).
   - `__syncthreads` always adds `mem_device` (`:14`). MLX uses `mem_threadgroup` almost everywhere.
   - Add a `__syncthreads_tg` macro for barriers that guard only threadgroup data (open question 3).
   - At MSL 3.2 and 4.0, fetch-and-modify atomics are relaxed-only and acquire and release are undeclared, so order a relaxed `fetch_add` with seq_cst fences (`__threadfence`). MSL 4.1 accepts acquire, release and acq_rel on fetch-and-modify in the overloads that take a mem_flags argument (`metal_atomic:1877`; the 3-argument form stays relaxed-only, `:566`), so one `atomic_fetch_add_explicit(p, v, memory_order_acq_rel, mem_flags::mem_device)` can replace the fence pair. Whether that is cheaper on AGX is unmeasured.
8. **Host wait.** The brief's `signaledValue` spin is the shippable path. MLX's fast-synch spin fence uses `#pragma METAL internals` and `thread_scope_system` (value 3), and has an open wedge bug (mlx #3142). Lab probe only.

M2: all of this is Apple7+ and macOS 15+, except `barrier(afterQueueStages:)` (macOS 26) and anything MSL 4.1 (macOS 27). Key the kernel source on OS version as well as GPU family. MLX picks the language version from the OS (`device.cpp:65-80`).

## 4. How to see inside a kernel on the Studio

OpenMM compiles kernels at runtime from generated source. The workflow is:
1. Dump that source.
2. Compile it offline with matching options for ISA and register data.
3. Capture a real step for timing and counters.

Step 0, one-time setup:
- Check `xcrun metal --version`. If the Metal Toolchain component is missing, `xcodebuild -downloadComponent MetalToolchain` installs it. Since Xcode 26 it ships separately (report 5 hit this on Xcode 27.0).
- Run `xcrun metal-arch` to confirm the Ultra's arch string (expect `applegpu_g15d`).

Step 1, dump the runtime source:
- Run `OPENMM_SAVE_TEMPS=1 OPENMM_SAVE_TEMPS_PREFIX=/tmp/openmm-metal-bench/src/ <python> benchmark.py --platform Metal --test pme ...`.
- `MetalContext.cpp:408-478` writes each module as `<prefix><hash>.metal`, with all defines, and prints `Source code: <file>`.

Step 2, compile offline with the runtime's options:
- AIR: `xcrun -sdk macosx metal -std=metal3.2 -fmetal-math-mode=safe -fmetal-math-fp32-functions=precise -c K.metal -o K.air`.
- Native (flags per the 32023.864 `metal.1` and `metal-pipelines-script.5` man pages; confirm with `xcrun metal --help` on 32023.922): `xcrun -sdk macosx metal -arch applegpu_g15d K.air -N K.mtlp-json -o K.metallib`.
  - The `.mtlp-json` pipelines script sets `compute_function`, `max_total_threads_per_threadgroup` and `threadgroup_size_is_multiple_of_thread_execution_width`.
  - Match these to the runtime pipeline, or the register allocation will differ.
- Disassemble: `xcrun metal-objdump --macho -d --reflection --build-table K.metallib > K.s`.
- Unsupported extra: `metal-nt -mllvm -print-agx3-static-sim-stats`, and a "[Performance Stats] Instructions/Registers" print. Both were found as strings in `libapplegpu-nt.dylib` (RE). If they work on g15 they give GPR count and occupancy requirement with no GPU run. Unverified.
- For VkFFT kernels, set `keepShaderCode` in the config and feed the dumped MSL through the same path.

Step 3, the in-process proxy. At pipeline creation in `MetalContext::getKernel`, log `maxTotalThreadsPerThreadgroup()`, `threadExecutionWidth()` and `staticThreadgroupMemoryLength()`. A value below 1024 flags register pressure on the M2. On Apple9 it may stay at 1024 regardless (Fink), so use counters there.

Step 4, headless capture and profile. M3 and later only for `profile run`. Commands verified against the local man pages, Xcode 27.0.
1. Launch the benchmark with `MTL_CAPTURE_ENABLED=1` and let it warm up.
2. `gpucapture list` finds the pid, and `gpucapture boundaries --pid P` shows the boundaries.
3. `gpucapture start --pid P --count 6 --output /tmp/openmm-metal-bench/ultra-profiler/pme.gputrace` captures 6 command buffers, which is 3 steps.
   - Label the default queue to use `--label`.
   - For a clean window, add an `MTLCaptureScope` around N steps in a lab build and use the Scope boundary.
   - `MTLCAPTURE_WAIT_FOR_SIGNAL=1` halts at device creation, which captures setup, not steady state.
4. `gpudebug -q --json -t pme.gputrace -c "profile run --gpu-state high --exec serial"` creates a session and prints its id. Then:
   - `gpudebug -s ID --json -c "go performance/shaders" -c "list --all"` gives shader cost ranking.
   - `-c "go performance/commands"` gives per-dispatch ranking.
   - `-c "go performance/timeline/counters" -c "list --all"` lists counters, then `fetch <counter>` saves a JSON time series.
   - End with `gpudebug --terminate ID`.
   - `--exec serial` isolates each dispatch's cost. `overlapping` shows what concurrency buys. `--gpu-state high` pins clocks so runs compare.
5. Build pipelines with a descriptor `label` set to the kernel name. Otherwise every row is anonymous.

Step 5, counters through xctrace:
- Record: `xcrun xctrace record --instrument "Metal GPU Counters" --instrument "Metal Application" --instrument GPU --time-limit 10s --output run.trace --launch -- <python> benchmark.py ...`.
- Then `xcrun xctrace export --input run.trace --toc`, and `--xpath` on the `metal-gpu-counter-profile`, `shader-profiler` and "Top Performance Limiter" schemas.
- Exit code 54 with a valid `.trace` is a known xctrace quirk (perfscan #866).

Step 6, the counters to read, from 111374:
- Occupancy Manager Target: below 100% means throttling.
- L1 eviction rate and L1 residency by type: spill or thrash.
- Shader Launch Limiter: low means launch-bound. Check the SETTLE and Langevin chain and computeRange.
- LLC and MMU limiter against utilization: incoherent access in PME spread and the nonbonded gathers.
- Per-line cost heat maps and Shader Execution History need Xcode's GUI on the Studio.
- Per-line live-register counts are shown only on M5 (111431).

Step 7, in-process per-kernel time. Classic counter sample buffers sample only at stage boundaries on Apple silicon, so per-dispatch samples are empty by design (Apple doc). Use MTL4 timestamps (brief section 6), or one encoder per kernel in a profiling build.

## 5. Myths and corrections

1. "MSL 4.1 features are available." They need `LanguageVersion4_1`, which requires macOS 27, and the platform compiles at 3.2 (`MetalContext.cpp:483`). Gate on OS and family. This covers threadgroup `atomic_float`, acquire/release, and the barrier overloads.
2. "Acquire/release atomics make last-block reductions work." At the platform's 3.2 they don't exist: fetch-and-modify atomics are relaxed-only and acquire and release are undeclared. In 4.1 fetch-and-modify takes them only through the overloads with a mem_flags argument (`metal_atomic:566`, `:1877`, compile check in research/2026-09-25-ledger-questions.md, section 3). Spec 6.16.4.5 still says relaxed-only, which reads as pre-4.1 text. The partials buffer must also be `coherent(device)`, because device memory is only threadgroup-coherent by default (4.8). The brief's lever 4 omits both. MLX avoids the pattern with two passes, and there is no inter-threadgroup forward-progress guarantee for spin designs (5.2.3.6).
3. "computeRange is slow because it is memory-bound." It is one threadgroup by construction (`rangeKernelBlocks = 1`). It belongs to the PME atom sort, not the block sort.
4. "Concurrent dispatch is a MetalQueue flag." It is an encoder property (dispatchType) plus barriers. Every buffer is hazard-tracked (`MetalArray.cpp:55`), and Apple does document what tracking does inside a concurrent encoder: nothing. The app owns synchronization there (MTLDispatchType.concurrent), and dispatch's probe 1 raced with tracked buffers. Across two queues Apple scopes automatic synchronization to one MTLCommandQueue, so use events or MTLFence. Untracked buffers are not required for either.
5. "Residency sets save nothing because we use setBuffer." Apple ties residency to commit time and to GPU start latency. Worth one measurement, not a skip.
6. "Barriers and cross-queue sync need Metal 4 or events." Classic encoders have queue-stage barriers since macOS 26, and classic `MTLFence` works across queues.
7. "The M2 per-core numbers apply to M3." Dynamic caching changed occupancy. A17 Pro keeps 1024 threads where M1 Max drops to 384. The brief's "208 KB, 384 to 3072 threads per core" is itself unsettled: Mesa's table ends at 1024, and Turner's own estimates range from 208 to 378 KB. Measure occupancy on the Ultra.
8. "Raise numThreadBlocksPerComputeUnit for everything." Nonbonded and GBSA already run 2560 threads per core through `numForceThreadBlocks`. The 768-per-core cap hits only kernels launched through `executeKernel`: bonded, integration and utilities.
9. "`threadGroupSizeIsMultipleOfThreadExecutionWidth = true` is zero-risk." It is not. Several dispatches are not multiples of 32:
   - `copyInteractionCounts` launches 1 thread (`MetalNonbondedUtilities.cpp:423`).
   - `positionsKernelSize = min(1024, numBuckets)` and `rangeKernelSize = min(256, length)` can be any value (`MetalSort.cpp:61-75`).
   - Common kernels call `execute(1, 1)` (NoseHoover, CustomNonbonded).
   Apple says a violating dispatch gives undefined results. Set it per pipeline only where every launch is a known multiple.
10. "Set the max-threads hint in `MTLCompileOptions`." It applies to the whole library, and one module mixes kernels launched at 64 and at 1024. Use the per-kernel attribute or per-pipeline descriptor.
11. "findBlocksWithInteractions should drop `__syncthreads` for simdgroup barriers" and "Turner's simd_prefix change gives 39%". The kernel already runs one SIMD group per threadgroup with `SYNC_WARPS` and ballot compaction. Turner's baseline was a different kernel.
12. "The nonbonded rotation may hit the slow per-lane shuffle." `warpRotateLeft` is `simd_shuffle_rotate_down(x, 1)`, the uniform-delta 2-cycle form (verified).
13. "Float atomics on M2 are slow because of contention." The G13 ISA has no float atomic, so M2 runs a CAS loop. The brief's inference is right, now with ISA evidence.
14. "Fast math breaks df64 through rounding." fma, add and mul are correctly rounded in both modes (Tables 8.1 and 8.2). The failure lab 015 saw is reassociation, which cancels TwoSum. The fix is the same: safe math for df64.
15. "Counter sample buffers returning zeros is a macOS bug." Apple silicon supports only stage-boundary sampling, and the MTL4 counter heap is timestamp-only. Expected behavior.
16. "Profiling needs Xcode's GUI." `gpucapture` and `gpudebug profile run` do headless per-shader cost and counters on M3 and later. Per-line views still need the GUI.
17. "VkFFT's Metal backend is capped at 256 threads." The cap is written for DCT-IV. R2C could lift it, and VkFFT already compiles with fast math.
18. "M4 is Apple10." M3 and M4 are Apple9. oxDNA's M4 numbers and the M4 papers belong with the Ultra.
19. "Tensor ops or neural accelerators will help." Not for fp32 on Apple9 (Rigel: 1.05 to 1.21x over simdgroup_matrix). M5 gains are stated for fp16, bf16 and int, and MLX's fp32 path on M5 defaults to TF32.
20. "Apple publishes driver or compiler source." It does not. The AGX kexts, AGXCompilerCore and the native translators are binary-only. The documented floor is AIR, native compile and `metal-objdump`.

## 6. Open questions for microbenchmarks on the Ultra (and the M2)

1. **Is `memoryBarrier(resources:)` scoped?**
   - One concurrent encoder runs chain A, a 2 ms kernel writing bufA, next to chain B, 20 short kernels on bufB separated by `memoryBarrier(resources: [bufB])`.
   - Timestamp B's last kernel with an MTL4 timestamp, or put it in a separate encoder read by GPUEndTime.
   - Repeat with `memoryBarrier(scope: .buffers)`. If B finishes before A only in the first case, the barrier is resource-scoped.
   - Run on both chips.
2. **Tracked against untracked in a concurrent encoder.** Answered without a microbenchmark.
   - Apple's MTLDispatchType.concurrent page makes the app responsible for synchronizing commands in a concurrent encoder that access one resource.
   - dispatch's probe 1 (a concurrent encoder, every buffer tracked, no barriers) gave rel|dF| 0.83 to 0.85 and a GPU page fault. Tracking did not serialize the dispatches and did not protect them.
   - So memoryBarrier is the only correctness mechanism inside a concurrent encoder, and untracked buffers are optional (research/2026-09-25-ledger-questions.md, section 2).
3. **Cost of `mem_device` on `threadgroup_barrier`.**
   - Kernel: loop 1024 times over a threadgroup-memory exchange plus barrier. Threadgroups of 64 and 256, grid of 4x cores.
   - Variants: `mem_threadgroup` only, `mem_threadgroup | mem_device`, and the same with a device store per iteration.
   - Report ns per barrier. This decides the `__syncthreads_tg` macro.
4. **Device atomic cost across dies.**
   - One uint counter padded to 128 B. Sweep the threadgroup count from 1 to 240, each doing 4096 relaxed adds, both uncontended (one counter per threadgroup) and contended (one shared counter).
   - A throughput knee near 30 threadgroups or cores, absent on the M2, points to die crossing.
   - Repeat with SIMD-aggregated adds, one per SIMD group, to size the aggregation win.
5. **Where do sortShortList2's 48.5 us go?**
   - Time a 737-key block sort (dhfr) in four configurations: the kernel alone in its own encoder, the kernel plus `copyTo` blit, the kernel plus a compute copy, and the counting-sort replacement.
   - Use MTL4 timestamps or `gpudebug --exec serial`. The split says whether the gain is the kernel or the encoder switch.
6. **Pipeline hints and ISA.**
   - Compile computeNonbonded, the GBSA force kernel and the df64 SETTLE kernel from `OPENMM_SAVE_TEMPS` output with no hint, then with `max_total_threads_per_threadgroup(64)` plus the multiple-of-width flag.
   - Diff register count and spill instructions in `metal-objdump`, and time each with `gpudebug --exec serial --gpu-state high`.
   - Do it on g15d and g14.
7. **What does `/` compile to under `MathModeSafe` plus precise functions?**
   - A kernel doing `a[i]/b[i]`, `fast::divide`, `1.0f/b`, `rsqrt`, `sqrt` over 16M elements, arithmetic-bound with 8 ops per load.
   - Dump the ISA and time each. This settles whether single-precision tile code pays the 30-cycle divide today.
8. **Spread strategies.**
   - Synthetic 98³ grid with ApoA1-like sorted atoms and 5³ stencils. Compare:
     - Current split 64-bit fixed point
     - Device float atomics
     - Threadgroup float brick (MSL 4.1) with one flush
     - SIMD pre-reduced float atomics
     - On the M2 only: a threadgroup int32 fixed-point brick
   - Validate the grid against a double-precision CPU spread.
9. **Residency set latency.**
   - 40 shared buffers, 200 MB total, bound by `setBuffer`, with a trivial dispatch.
   - Measure GPUStartTime minus the host time just before commit, over 1000 commits, with and without a residency set on the queue.
   - Report the median and p99.
10. **Occupancy and grid multiplier for capped kernels.**
    - Run computeBondedForces and the Langevin step on apoa1 and dhfr with `numThreadBlocksPerComputeUnit` at 12, 16, 24 and 32.
    - Read Occupancy Manager Target and Shader Launch Limiter from `gpudebug`. Pick per family.
11. **DVFS under short dispatches.**
    - A 50 us reference kernel, timed alone, then after 40 dispatches of about 2 us each in the same command buffer.
    - Compare `gpudebug profile run` at `--gpu-state default` and `high`. If default mode times the reference slower after the short dispatches, fusing small kernels also buys back clock.
12. **`coherent(device)` cost.** Run computeRange rewritten as many threadgroups with a last-block reduce, with and without `coherent(device)` on the partials, against the MLX two-pass version. This decides whether single-pass reductions are worth the coherence qualifier at all.

### Findings

- OpenMM's Metal common.metal:16 defines __launch_bounds__(x) as empty, so no kernel carries a max-threads hint. MSL has [[max_total_threads_per_threadgroup(N)]] on kernel functions and the -fmax-total-threads-per-threadgroup compile flag; MTLCompileOptions.maxTotalThreadsPerThreadgroup (macOS 13.3) and MTLComputePipelineDescriptor.maxTotalThreadsPerThreadgroup do the same from the host. Apple tech talk 10580 says setting it lets the compiler allocate and spill registers better, and to pick the smallest multiple of the thread execution width that works. (source: MSL spec 4.1 section 5.1 kernel attributes; https://developer.apple.com/documentation/metal/mtlcompileoptions/maxtotalthreadsperthreadgroup; tech talk 10580 transcript; hipdelta-gbsa platforms/metal/src/kernels/common.metal:16; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: findBlocksWithInteractions (declared GROUP_SIZE), computeNonbonded tiles (THREAD_BLOCK_SIZE), GBSA tiles, computeBucketPositions (1024). Map __launch_bounds__(x) to [[max_total_threads_per_threadgroup(x)]] so register-heavy tile kernels get the right register budget. Cheapest possible experiment, one macro.)
- MetalContext.cpp:505 builds every pipeline with newComputePipelineState(function, options) and no descriptor, so threadGroupSizeIsMultipleOfThreadExecutionWidth stays at its default false. Apple's doc says setting it true lets Metal take advantage of additional optimizations; the dispatch must then always use threadgroup sizes that are multiples of threadExecutionWidth (32). (source: https://developer.apple.com/documentation/metal/mtlcomputepipelinedescriptor/threadgroupsizeismultipleofthreadexecutionwidth; metal-cpp MTLComputePipeline.hpp:121; MetalContext.cpp:505; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: All kernels, every dispatch. OpenMM already uses 32-multiple sizes (64, 128, 256, 1024), so switching to a descriptor with this flag plus maxTotalThreadsPerThreadgroup is a zero-risk compile-time change for nonbonded, GBSA, PME spread and bonded.)
- MSL 4.1 (spec dated 2026-06-04) adds memory_order_acquire, memory_order_release and memory_order_acq_rel to atomics and fences, and threadgroup_barrier/simdgroup_barrier gain overloads taking (mem_flags, memory_order, thread_scope). memory_order_seq_cst is labeled Metal 4 and later. atomic_thread_fence with thread_scope has existed since Metal 3.2. (source: MSL spec 4.1 sections 6.10.1 (barriers) and 6.16.1 to 6.16.4 (memory order, thread scope, fence); confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10 (FST row 'Acquire/release memory ordering atomics' starts at Apple7); openmm_use: computeRange last-block reduction, findBlocksWithInteractions interaction-count publication, and the __threadfence macro (common.metal:15, currently seq_cst device fence). Release/acquire fences are the spec-sanctioned and cheaper replacement for seq_cst.)
- In MSL 4.1, atomic fetch-and-modify functions (fetch_add, fetch_min, fetch_max, fetch_and, fetch_or, fetch_xor, fetch_sub) take acquire, release, acq_rel and seq_cst in the overloads with a mem_flags argument, as load, store, exchange and compare_exchange do. The 3-argument overloads stay relaxed-only, and so does every fetch-and-modify at 3.2 and 4.0, where acquire, release and acq_rel are undeclared. Spec 6.16.4.5 still says relaxed-only, while 6.16.1 says 4.1 lets you specify memory_order for atomic operations; the header and the compiler follow 6.16.1. At 3.2 the last-block pattern is a seq_cst device fence (`__threadfence`, common.metal:15), a relaxed atomic_fetch_add on the counter, then a seq_cst fence in the block that observes the final count. After a 4.1 bump it can be one atomic_fetch_add_explicit(counter, 1, memory_order_acq_rel, mem_flags::mem_device). (source: metal_atomic in MetalToolchain 27.2, :566, :1877, :1884; compile check experiments/028-ultra-max/research-data/ledger-q/atomics41.metal; MSL spec 4.1 sections 6.16.1 and 6.16.4.5; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: computeRange (sort.metal:95-130), any 'last threadgroup finishes the reduction' pattern, and the 64-bit fixed-point force counters. Whether AGX emits anything cheaper for the acq_rel fetch_add than for the fence pair is unmeasured.)
- By default device-address-space memory is only threadgroup coherent. Writes from one threadgroup are guaranteed visible to another threadgroup in the same dispatch only if the buffer is declared with the coherent(device) qualifier (Metal 3.2+, FST 'Memory coherence' row from Apple6). OpenMM's computeRange has the last threadgroup read range[] written by other threadgroups through a plain device pointer plus __threadfence, which the spec does not guarantee. (source: MSL spec 4.1 section 4.8 (memory coherence) and 2.x coherent qualifier; Feature Set Tables May 2026 'Memory coherence' row; hipdelta-gbsa sort.metal:95-130; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: computeRange and any cross-threadgroup handoff (findBlocksWithInteractions overflow counters). Today it works because MetalSort.cpp:62-65 runs computeRange as one threadgroup, but any move to many threadgroups needs coherent(device) or pure atomics.)
- computeRange runs as a single threadgroup of 256 threads (MetalSort.cpp:62-65 sets rangeKernelSize=256, rangeKernelBlocks=1) and does a grid-stride min/max plus a threadgroup tree reduction with a full barrier per level. Metal offers simd_min/simd_max (SIMD-group reduction, one instruction family) and relaxed atomic_fetch_min/max on uint in device memory, which allows a many-threadgroup version with no last-block handoff at all by encoding floats as order-preserving uint keys. (source: MSL spec 4.1 sections 6.9.2 (SIMD-group reduction functions) and 6.16.4.5 (atomic_fetch_min/max on int/uint); MetalSort.cpp:62-65; sort.metal:95-130; confidence: inferred; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: computeRange, measured at 250 us per step on apoa1ljpme. One threadgroup on a 60-core M3 Ultra leaves 59 cores idle; a grid of about 2x core count threadgroups with simd_min/max then one relaxed atomic per SIMD-group should cut this to tens of microseconds.)
- MSL states forward progress only between SIMD-groups in the same threadgroup. It states no forward-progress guarantee between threadgroups of a dispatch, so single-pass algorithms that spin on another threadgroup's flag (decoupled look-back scans, persistent-kernel work queues) are not guaranteed to terminate. (source: MSL spec 4.1 section 5.2.3.6 (forward progress); confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Sort pipeline (computeBucketPositions, sortShortList2) and any plan for a one-pass prefix scan in the neighbor list. Use multi-pass scans or atomics-only designs, not look-back spins.)
- The sort path for short lists calls buckets.copyTo(...) (MetalSort.cpp:106-107), which MetalArray.cpp:99-101 implements with a blitCommandEncoder copyFromBuffer. In classic Metal that ends the current compute encoder and starts a blit encoder, then a new compute encoder. MTL4ComputeCommandEncoder has copyFromBuffer and fillBuffer inside the unified compute encoder (metal-cpp MTL4ComputeCommandEncoder.hpp:67,91), and WWDC25 205 describes the unified compute encoder that holds dispatches, blits and acceleration-structure builds. (source: metal-cpp MTL4ComputeCommandEncoder.hpp:67,91; https://developer.apple.com/videos/play/wwdc2025/205/; MetalSort.cpp:106-107; MetalArray.cpp:99-101; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10 (Metal 4 needs macOS 26+); openmm_use: sortShortList2 (48.5 us per step) and every copyTo in the step. In classic Metal, replace the blit with a tiny compute copy kernel or ping-pong buffer pointers so the step stays in one compute encoder; the MTL4 route is only worth it if the port happens anyway.)
- Buffers created from MTLDevice default to MTLHazardTrackingModeTracked; heap-allocated resources default to untracked. With tracking on, Metal delays a write to a tracked resource until prior reads finish and blocks later commands until the write completes, and Apple says untracked resources can improve runtime performance. MTL4 command queues ignore hazardTrackingMode entirely, as do resources reached only through argument buffers. MetalArray.cpp:55 creates all buffers as StorageModeShared with default (tracked) hazard tracking. (source: https://developer.apple.com/documentation/metal/mtlhazardtrackingmode, /tracked, /untracked; https://developer.apple.com/documentation/metal/memory-heaps; MetalArray.cpp:55; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Per-step orchestration. Any plan for concurrent dispatch or a second PME queue is undercut by automatic tracking, which serializes on shared buffers (force accumulator, posq). Setting ResourceHazardTrackingModeUntracked is a prerequisite for those plans, with explicit barriers taking over.)
- Apple's MLX Metal backend, a production Apple-authored compute stack, creates all buffers as ResourceStorageModeShared | ResourceHazardTrackingModeUntracked (allocator.cpp:16), uses commandBufferWithUnretainedReferences (device.cpp:323,559), and opens encoders with computeCommandEncoder(MTL::DispatchTypeConcurrent) (device.cpp:580). It tracks read-after-write and write-after-read hazards in software and issues memoryBarrier(MTL::BarrierScopeBuffers) only when the next dispatch reads a prior output or overwrites a prior input (device.cpp:343-400). (source: github.com/ml-explore/mlx@77e1cfb mlx/backend/metal/allocator.cpp:16, device.cpp:323,343-400,559,580; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Per-step orchestration across all 18 to 47 dispatches. This is a working template for OpenMM: untracked buffers, concurrent encoder, barrier inserted only on a real dependency. Independent kernels (bonded vs PME spread vs nonbonded) then overlap without a second queue.)
- MLX uses one MTLFence per encoder: the new encoder waitForFence on fences of earlier encoders that produced its inputs, and calls updateFence at its end (device.cpp:430-495). Apple's resource-synchronization doc says MTLFence in classic Metal works across command queues on the same device, while MTL4 needs MTLEvent for cross-queue ordering. (source: mlx device.cpp:430-495; https://developer.apple.com/documentation/metal/resource-synchronization; https://developer.apple.com/documentation/metal/synchronizing-passes-with-a-fence; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Second PME queue plan in the brief: a classic MTLFence (not a shared event plus host wait) is enough to join the PME queue back into the main queue before force reduction, with no CPU involvement.)
- Apple ranks synchronization mechanisms by scope: intrapass barrier, fence, intraqueue barrier (consumer/producer), MTLEvent, MTLSharedEvent, and advises picking the smallest scope because larger scopes stop the GPU from doing more work. Atomic-type accesses need no synchronization. Classic MTLComputeCommandEncoder also gained barrier(afterQueueStages:beforeStages:) in macOS 26, which Apple says lets Metal reorder the exact point of the barrier. (source: https://developer.apple.com/documentation/metal/resource-synchronization; https://developer.apple.com/documentation/metal/mtlcommandencoder/barrier(afterqueuestages:beforestages:); metal-cpp MTLCommandEncoder.hpp:61; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10 (queue barriers need macOS 26); openmm_use: Per-step orchestration. OpenMM's two command buffers and the host wait are the widest scope; the in-encoder memoryBarrier is the narrowest. Collapse to one command buffer with intrapass barriers where the host does not need data.)
- MTL4 intrapass barriers (barrierAfterEncoderStages, barrierAfterStages with MTLStageDispatch) are stage-granular with MTL4VisibilityOptions device or resourceAlias; there is no per-resource barrier in the MTL4 compute encoder. Classic memoryBarrier(resources:) exists and Apple describes it as making passes finish updating resources before dependent stages, but does not say the hardware scopes the wait to those resources. (source: https://developer.apple.com/documentation/metal/synchronizing-stages-within-a-pass; https://developer.apple.com/documentation/metal/mtl4visibilityoptions; https://developer.apple.com/documentation/metal/mtlcomputecommandencoder/memorybarrier(resources:); metal-cpp MTL4CommandEncoder.hpp:50-54; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Per-step orchestration. Assume every barrier drains all in-flight dispatches in the encoder; group independent kernels (bonded, PME spread, nonbonded) before one barrier rather than barrier-per-kernel.)
- Metal Feature Set Tables (May 21, 2026) put 64-bit atomics (atomic_ulong min/max) at Apple9 and later (footnote 7), floating-point atomics and acquire/release atomics at Apple7, SIMD shift and fill at Apple8, memory coherence and residency sets at Apple6, nonuniform threadgroups at Apple4, indirect dispatch arguments at Apple3. Family map in the FST: M1 is Apple7, M2 is Apple8, M3 and M4 are Apple9, M5 and A19 are Apple10. (source: https://developer.apple.com/metal/Metal-Feature-Set-Tables.pdf (May 21, 2026), GPU family and feature availability tables, footnote 7; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Capability gating for all kernels. 64-bit atomics cannot replace the split 32-bit fixed-point force accumulation on M1/M2, so the split path must stay as a fallback; Apple10-only rows are graphics features with no nonbonded or PME use.)
- FST limits: setBytes inline data max 4 KB; threadgroup memory 32 KB per threadgroup with 16-byte alignment; max fences 32,768; performance-counter heaps 32 per process. Footnote 5: the real max threads per threadgroup for a kernel is whatever the pipeline's maxTotalThreadsPerThreadgroup reports, which can be below 1024 when register use is high. (source: Metal Feature Set Tables May 21, 2026, implementation limits tables and footnote 5; https://developer.apple.com/documentation/metal/mtlcomputepipelinestate/maxtotalthreadsperthreadgroup; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: computeBucketPositions and any 1024-thread kernel must check pipeline.maxTotalThreadsPerThreadgroup at load time; GBSA and nonbonded tile sizing must fit tiles plus scratch inside 32 KB threadgroup memory.)
- MTLLanguageVersion version4_1 requires macOS 27.0 and version4_0 requires macOS 26.0. OpenMM Metal compiles at LanguageVersion3_2 (MetalContext.cpp:483). Metal 4.1 features (threadgroup atomic_float add/sub, acquire/release barriers and atomics, placement new) are therefore unavailable unless the runtime compile bumps the language version, and the fallback must key on OS version as well as GPU family. (source: https://developer.apple.com/documentation/metal/mtllanguageversion/version4_1 and /version4_0; metal-cpp MTLLibrary.hpp:73-74 (LanguageVersion4_0=262144, 4_1=262145); MetalContext.cpp:483-485; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10 (OS-gated, macOS 27+); openmm_use: PME gridSpreadCharge float-atomic work (lab 011) if it wants threadgroup-memory float atomics for a tiled spread, and the fence rewrite in computeRange. Needs an OS check before choosing the 4.1 kernel source.)
- MSL 4.1 adds atomic_float fetch_add and fetch_sub in threadgroup memory (earlier versions allowed atomic_float only in device memory). This enables a two-level spread: accumulate a local PME brick in threadgroup memory with native float atomics, then flush to the device grid once per threadgroup. (source: MSL spec 4.1 section 6.16 atomic types table and 'New in Metal 4.1' list; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10 (needs MTLLanguageVersion4_1, macOS 27); openmm_use: gridSpreadCharge (16 to 27 percent of PME test time). Tech talk 10580 separately says global atomics became a primary bottleneck on large Apple GPUs and to use threadgroup atomics first; this is the official route to do that with floats.)
- Precise math mode (Table 8.1) makes x/y, 1/x, sqrt and rsqrt correctly rounded. Fast mode (Table 8.2) gives x/y at 2.5 ulp, rsqrt at 2 ulp and implements sqrt as x*rsqrt(x). fma, add and mul are correctly rounded in both modes. OpenMM compiles with MathModeSafe and MathFloatingPointFunctionsPrecise (MetalContext.cpp:484-485), while CUDA OpenMM uses fast math. The metal::precise:: and metal::fast:: namespaces select precision per call regardless of the global mode. (source: MSL spec 4.1 section 8.1 and Tables 8.1, 8.2; section 6.5 math function namespaces; MetalContext.cpp:484-485; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Nonbonded and GBSA tile inner loops (rsqrt, division in Born radii and chain rule), bonded angle and torsion math, PME reciprocal. Switch hot single-precision paths to metal::fast::rsqrt and fast division while keeping precise:: in df64 and constraint code; since fma/add/mul stay correctly rounded, df64 arithmetic is unaffected by the global mode.)
- Precise and fast modes may both flush single-precision denormals to zero on Apple GPUs per MSL section 8.1; Apple gives no switch to force denormal support. (source: MSL spec 4.1 section 8.1 (floating-point precision and denormals); confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: df64 SHAKE, SETTLE and Langevin chains (about 50 us per step): the low word of a df64 pair can be denormal near small values and flush to zero, so df64 error bounds from CPU references do not transfer exactly. Test near-zero displacements explicitly.)
- Residency sets reduce the latency between commit and GPU start. Apple's residency-set article says resources named through encoder calls are made resident right after the command buffer commits, which can delay when the GPU starts on it; a residency set attached to the queue with requestResidency() called ahead of time avoids that. Up to 32 sets per queue or command buffer. MLX attaches residency sets to its queue with the comment 'Metal locks a command buffer's residency at commit time' (device.cpp:517). (source: https://developer.apple.com/documentation/metal/simplifying-gpu-resource-management-with-residency-sets; https://developer.apple.com/videos/play/wwdc2025/205/; mlx device.cpp:517, resident.cpp; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10 (FST from Apple6, macOS 15+); openmm_use: Per-step orchestration: two command buffers per step each pay commit-time residency work for every setBuffer-bound buffer. One residency set holding all OpenMM context buffers, attached to the queue once, targets the commit-to-start gap. Whether setBuffer-bound (not useResource) buffers pay the same cost is my inference.)
- commandBufferWithUnretainedReferences skips retain/release of every bound resource; Apple reserves it for extremely performance-critical cases where the app keeps resources alive itself. OpenMM MetalQueue.cpp:47 uses the default retained commandBuffer(). (source: https://developer.apple.com/documentation/metal/mtlcommandqueue/makecommandbufferwithunretainedreferences(); https://developer.apple.com/documentation/metal/mtlcommandbufferdescriptor/retainedreferences; MetalQueue.cpp:47; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Per-step CPU encode cost over 18 to 47 dispatches. OpenMM's buffers live for the context lifetime, so unretained command buffers are safe and cut encode-side overhead; MLX does exactly this.)
- Indirect dispatch reads the grid size from a GPU buffer (dispatchThreadgroups(indirectBuffer:indirectBufferOffset:threadsPerThreadgroup:) in classic Metal, dispatchThreads(indirectBuffer:) in MTL4 using MTLDispatchThreadsIndirectArguments). A kernel can write zero threadgroups to skip the next dispatch without a host round trip. (source: https://developer.apple.com/documentation/metal/mtl4computecommandencoder/dispatchthreads(indirectbuffer:); https://developer.apple.com/documentation/metal/mtldispatchthreadsindirectarguments; FST 'Indirect dispatch' row (Apple3+); metal-cpp MTL4ComputeCommandEncoder.hpp:86; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: findBlocksWithInteractions currently launches its full grid every step and early-exits when rebuildNeighborList[0]==0 (findInteractingBlocks.metal:306). Having sortBoxData write the indirect args (full grid or zero) removes the launch and scheduling cost on non-rebuild steps, which is most steps.)
- In a compute ICB (MSL 6.17.2) dispatches are always concurrent, barriers encoded inside the ICB do not affect the parent encoder, set_compute_pipeline_state is only usable with argument buffers, and there is no setBytes equivalent; constants must live in buffers. (source: MSL spec 4.1 section 6.17.2 (compute_command, concurrent_dispatch_threadgroups, set_barrier/clear_barrier); confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: GPU-driven CCMA and SHAKE iteration loops from the brief. OpenMM passes per-dispatch scalars through setBytes (MetalContext.cpp:605-610), so an ICB port must first move those scalars into a small constants buffer, and every dependent step inside the ICB needs set_barrier.)
- MTL4 argument tables bind by GPU address only (setAddress, setResource, setTexture, setSamplerState); there is no setBytes in the MTL4 compute encoder. (source: https://developer.apple.com/documentation/metal/mtl4argumenttable; metal-cpp MTL4ComputeCommandEncoder.hpp:108 and MTL4ArgumentTable.hpp; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10 (macOS 26+); openmm_use: Per-step orchestration. Any MTL4 port touches every kernel launch that uses setBytes for step-varying scalars (integrator dt, PME grid parameters); plan a ring buffer of small constant blocks.)
- Tech talk 10580 (Metal compute on Apple silicon Macs) lists concrete kernel rules: use signed int loop indices because unsigned wraparound blocks vectorized loads; use the constant address space for read-only inputs; avoid dynamically indexed stack arrays; prefer 16-bit types where precision allows to save registers; minimize device atomics because on large GPUs they become a primary bottleneck, reducing in threadgroup memory first. (source: https://developer.apple.com/videos/play/tech-talks/10580/ transcript; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10 (talk targets M1 Pro/Max, advice general); openmm_use: computeBondedForces (11 to 16 percent, uint loops over bond indices and per-atom device atomics), GBSA tiles, nonbonded tiles. Audit hot loops for uint counters and runtime-indexed local arrays; route per-atom force atomics through a SIMD-group reduction where atoms repeat.)
- MLX's custom-kernel documentation tells users to reduce across each simdgroup first before atomic_fetch_add on floats because that is much faster than atomics alone, and exposes a math_mode 'relaxed' compile option. (source: Context7 /websites/ml-explore_github_io_mlx_build_html, dev/custom_metal_kernels page; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Bonded force accumulation and GBSA Born-sum accumulation: when a SIMD-group's lanes hit the same atom (clustered bonded terms, tile rows), simd_sum before one atomic cuts atomic traffic by up to 32x.)
- MLX kernels/atomic.h notes that Metal's atomic_compare_exchange_weak_explicit on float is not bitwise: under no-NaNs fast math it lowers to 'fcmp fast ueq', so a CAS loop never succeeds while memory holds NaN. MLX's native atomic types are int, uint, ulong and float. (source: github.com/ml-explore/mlx@77e1cfb mlx/backend/metal/kernels/atomic.h; confidence: measured-by-third-party; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Any float CAS emulation (for example an atomicMax on float in energy or range code). Do CAS on the uint bit pattern via as_type, not on atomic_float, or a NaN hangs the kernel.)

### Corrections to the brief

1. The brief lists "MSL 4.1 features" as if they were simply available. MTLLanguageVersion4_1 needs macOS 27.0, and version4_0 needs macOS 26.0. The platform compiles at LanguageVersion3_2 (MetalContext.cpp:483). So threadgroup atomic_float, acquire/release atomics and barriers, and placement new all need a language-version bump plus an OS check. A GPU-family check alone is not enough.
2. The brief implies acquire/release applies to all atomics. In 4.1 that holds for fetch-and-modify only in the overloads with a mem_flags argument (`metal_atomic:1877`, compile check). The 3-argument form stays relaxed-only (`:566`), and spec 6.16.4.5 still says relaxed-only, which reads as pre-4.1 text. At the platform's 3.2, ordering comes from seq_cst fences around a relaxed fetch_add.
3. Device memory is threadgroup-coherent by default (spec 4.8). Any cross-threadgroup handoff needs coherent(device), including the computeRange last-block pattern and anything like it. OpenMM declares no coherent buffers, and its __threadfence macro does not supply that guarantee.
4. The brief says to skip residency sets. Apple's residency-set article and MLX's comment (device.cpp:517) both say residency is resolved at commit time and can delay the GPU start. That makes residency sets a commit-to-start latency tool for per-step orchestration. They are not only a replacement for useResource, so they deserve a cheap trial.
5. Barriers are not MTL4-only. Classic MTLComputeCommandEncoder gained barrier(afterQueueStages:beforeStages:) in macOS 26. Classic MTLFence works across command queues on one device, which suits the second-PME-queue plan without events. MTL4 needs events for cross-queue ordering.
6. Hazard tracking does not block the brief's concurrency plans. Device-created buffers default to tracked, and OpenMM uses tracked shared buffers everywhere. Tracking gives no synchronization inside a concurrent encoder, so the app adds memoryBarrier calls there, and between passes it delays only commands that conflict with a write. Across two queues Apple documents no automatic synchronization; use events or MTLFence. MLX's untracked buffers with a concurrent encoder and software RAW/WAR barriers are one working template, not a prerequisite.
7. GPU family naming: per the May 2026 FST, M3 and M4 are both Apple9, and Apple10 is M5/A19. Any brief text treating M4 as Apple10 is wrong.
8. computeRange's 250 us per step comes from its launch configuration. It runs as one threadgroup of 256 threads (MetalSort.cpp:62-65), so the fix is a many-threadgroup reduction and not a finer barrier choice. computeBucketPositions is also a single 1024-thread threadgroup.
9. Apple's spec now steers users away from simdgroup_matrix toward MPP/tensor ops. The M5 Neural Accelerator gains are stated for fp16, bf16 and int only, so none of that path helps OpenMM's fp32 kernels.

### Gaps

1. Apple does not say whether memoryBarrier(resources:) waits only on the listed resources or drains the whole encoder. Apple also publishes no numbers for the GPU cost of a dispatch barrier or of an encoder switch.
2. Apple has no documentation on threadgroup memory bank layout or bank conflicts for Apple7 through Apple10.
3. Apple publishes no GPU driver or firmware source. Its open-source compute code is MLX and metal-cpp, and both were read. The reverse-engineered sources (Asahi, dougallj applegpu) belong to another family, so I did not read them here.
4. MLX's fast-synch path uses the undocumented thread_scope_system and '#pragma METAL internals'. Nothing guarantees it keeps working across macOS releases.
5. I did not read the Metal Performance Primitives programming guide PDF or the archived Metal Best Practices Guide.
6. The spec does not say which compile option switches plain '/' from correctly rounded to 2.5 ulp. The precision tables are tied to the math mode, and -fmetal-math-fp32-functions defaults to fast, but OpenMM's precise setting and how the two interact for the '/' operator should be confirmed by compiling a test.
7. I found no WWDC26 compute session beyond the ML and tensor material. I could not find a public statement of Apple10 fp32 throughput or of fp32 support on the Neural Accelerators.
8. Two claims here are my inference and have no Apple number behind them: that setBuffer-bound buffers pay commit-time residency cost, and that uniform<T> or private storage give measurable speedups. None of this was measured, since the task barred GPU runs.
9. Two doc pages returned 404 through the DocC JSON endpoint: MTLSharedEvent waitUntilSignaledValue(_:timeoutMS:) and documentation/updates/metal. Their content is not reflected here.

### Findings

- On Apple9, register memory is no longer reserved at a shader's worst-case maximum for the whole SIMD group lifetime. It is allocated dynamically. The register file is a cache, and threadgroup, tile, stack and buffer memory now share fewer, larger on-chip caches. (source: https://developer.apple.com/videos/play/tech-talks/111375/ at 9:53 and 11:15-11:46; confidence: official; gpu_families: Apple9 (M3, M4), Apple10 (M5, second generation); openmm_use: nonbonded and GBSA pair tiles, findBlocksWithInteractions. Big register footprints in rarely taken branches (exclusion handling, cutoff tails) cost less occupancy on M3/M4 than on M1/M2, so splitting kernels to cut peak registers pays mainly on Apple7/8.)
- On Apple9 the occupancy manager lowers occupancy to prevent cache spills, so occupancy now depends on how much threadgroup, tile, stack and buffer data a kernel touches, not only on registers. (source: https://developer.apple.com/videos/play/tech-talks/111375/ at 13:04-13:30; confidence: official; gpu_families: Apple9, Apple10; openmm_use: computeNonbonded and GBSA tiles stage 32-atom tiles in threadgroup memory. Large per-thread working sets plus threadgroup staging now throttle occupancy directly; measure with the Occupancy Manager Target counter before and after any staging change.)
- Apple9 guidance: if threadgroup memory is used mainly as a software-managed cache of device or constant buffer data, reading the buffers directly may be faster, because both go through the same cache hierarchy and the copy adds barriers and occupancy cost. (source: https://developer.apple.com/videos/play/tech-talks/111373/ at 11:43-12:46; confidence: official; gpu_families: Apple9, Apple10; openmm_use: sortShortList2 (48.5 us per step) stages keys into threadgroup keyBuffer between two __syncthreads and then every thread reads keyBuffer[i] with the same i. That is exactly the pattern Apple says may be slower on M3. Candidate A/B: read device memory directly, or load one key per lane and broadcast with simd_shuffle. Same question applies to the posq/tile staging in computeNonbonded.)
- Apple9 can issue FP32, FP16 and integer instructions in parallel from different SIMD groups, up to 2x ALU throughput, but only when several SIMD groups with a mix of instruction types are resident. FP16 runs at full rate and float/half conversions are free. (source: https://developer.apple.com/videos/play/tech-talks/111375/ at 14:19-15:04; https://developer.apple.com/videos/play/tech-talks/111373/ at 13:08-14:35; confidence: official; gpu_families: Apple9, Apple10; openmm_use: Nonbonded pair tiles mix float math with integer exclusion-bit and index work, and the 64-bit fixed-point force path is integer heavy. The dual issue only helps with enough resident SIMD groups, which ties it to the grid-size finding below.)
- Apple's rule for filling the GPU is 1K to 2K concurrent threads per shader core. The Metal platform's persistent-thread grid is numThreadBlocksPerComputeUnit=12 times 64 threads, which is 768 threads per core on every family. (source: https://developer.apple.com/videos/play/wwdc2022/10159/ at 5:21-7:08; /Users/amir/code/mini/hipdelta-gbsa/platforms/metal/src/MetalContext.cpp:68-69,158,172; confidence: inferred; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: findBlocksWithInteractions, computeNonbonded, GBSA tiles and computeBondedForces all size to numThreadBlocks. Raising the multiplier to 16 to 32 (1024 to 2048 threads per core) is a one-line A/B that follows Apple's rule directly. Occupancy counters will say whether the kernels are register or L1 bound first.)
- Setting maxTotalThreadsPerThreadgroup (or [[max_total_threads_per_threadgroup]]) lets the compiler plan register allocation and spill more efficiently. Apple recommends the smallest multiple of the execution width that fits. threadGroupSizeIsMultipleOfThreadExecutionWidth enables 'additional Metal optimizations' and defaults to false. The platform builds pipelines with newComputePipelineState(function, options, reflection) and no descriptor, so both are left at defaults and no kernel carries the attribute. (source: https://developer.apple.com/videos/play/tech-talks/10580/ at 19:45-20:12; Apple doc pages threadgroupsizeismultipleofthreadexecutionwidth and maxtotalthreadsperthreadgroup; /Users/amir/code/mini/hipdelta-gbsa/platforms/metal/src/MetalContext.cpp:505; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Every kernel. Launch sizes are fixed at 64 (force kernels) or 32 (findBlocksWithInteractions), so a MTLComputePipelineDescriptor with the multiple-of-width flag true and maxTotalThreadsPerThreadgroup set to the real block size is cheap to try. Biggest expected effect on register-heavy kernels: computeNonbonded, GBSA, SETTLE/SHAKE in df64.)
- Resources created from an MTLDevice default to hazard tracking, heap resources default to untracked, and Metal 4 queues ignore tracking entirely. Resource-level tracking creates false dependencies between passes that touch different parts of one buffer; Apple's fix is to split resources or mark them untracked and synchronize with fences or events. (source: https://developer.apple.com/documentation/metal/resource-synchronization; https://developer.apple.com/documentation/metal/mtlhazardtrackingmode; https://developer.apple.com/videos/play/wwdc2020/10632/ at about 6:05-6:32; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: per-step orchestration and PME second queue. MetalArray.cpp:55 creates every buffer with ResourceStorageModeShared and no untracked flag. The shared force and posq buffers used by both the PME queue and the main queue are tracked, so the driver may serialize work Apple would let overlap. Test HazardTrackingModeUntracked on arrays the platform already orders with explicit events.)
- Metal does not require synchronization between passes for atomic-type accesses, and Apple advises choosing the smallest-scope synchronization mechanism that covers the dependency. (source: https://developer.apple.com/documentation/metal/resource-synchronization; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Force accumulation into the 64-bit fixed-point buffer is atomic-only across nonbonded, PME interpolate and bonded kernels. Those dispatches can be marked concurrent without a barrier between them if the only shared writes are atomics; only the final reduce needs a barrier.)
- On Apple GPUs a serial compute dispatch guarantees that every memory write is visible to all shader cores before the next dispatch starts, which implies a coherency flush. Threadgroup (tile) memory is not persistent across dispatches in a compute encoder. (source: https://developer.apple.com/videos/play/wwdc2021/10153/ at 5:40-5:55 and 20:43-21:00; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: per-step orchestration. With 18 to 47 dispatches per step, each serial boundary costs a flush plus drain. This backs the lab's 1.88 us per serial dispatch figure and argues for concurrent dispatch with explicit barriers only where kernels read the previous kernel's output.)
- Batch many encoders into one command buffer to avoid GPU bubbles, use large grids, and use concurrent dispatch when individual kernels have small thread counts. (source: https://developer.apple.com/videos/play/tech-talks/10580/ at 8:58-10:25; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: per-step orchestration for small systems. gbsa (293 us) and rf (502 us) run many kernels with tiny grids (integration, SETTLE, computeRange, reductions). Concurrent dispatch of the independent ones (bonded next to nonbonded, PME spread next to direct space) is Apple's prescribed fix.)
- Shader Launch Limiter is the counter that shows a workload too small to fill the GPU; Apple's example read 0.07%. Large threadgroup memory allocations also stall shader launches. (source: https://developer.apple.com/videos/play/tech-talks/111374/ at 18:25-20:11; confidence: official; gpu_families: Apple9, Apple10 (counter introduced with M3 tools); openmm_use: per-step orchestration and small kernels. Profile the SHAKE/SETTLE/Langevin df64 chain (about 50 us) and computeRange with this counter. A low value confirms launch-bound kernels that should be fused or run concurrently rather than tuned.)
- Occupancy Manager Target shows when the occupancy manager is throttling. L1 eviction rate, L1 load/store bandwidth and L1 residency split by memory type (buffer, threadgroup, stack, register) show which data is thrashing. If the LLC limiter is far above its utilization the cache is thrashing; if the MMU limiter is above its utilization, incoherent buffer access is causing TLB misses. (source: https://developer.apple.com/videos/play/tech-talks/111374/ at 20:50-25:25; confidence: official; gpu_families: Apple9, Apple10; openmm_use: nonbonded, GBSA and PME spread. gridSpreadCharge scatters atoms to a 3D grid and computeNonbonded gathers neighbor atoms through interacting-tile lists; both are the incoherent pattern the MMU limiter catches. These are the counters to capture before any kernel rewrite.)
- On M5, the occupancy manager throttles for four reasons exposed as occupancy target influence counters: live registers held too long, private memory above on-chip capacity (spills show up as L1 pressure), LLC/MMU/DRAM backpressure, and texture decompression. Xcode 26.4 shows live register count per source line. (source: https://developer.apple.com/videos/play/tech-talks/111431/ at 3:17-6:49 and 21:54-26:42; confidence: official; gpu_families: Apple10 (per-line live registers may need M5; unverified on M3); openmm_use: nonbonded and df64 integration. The df64 SHAKE/SETTLE kernels and the pair-interaction inner loop hold many live registers. Per-line live-register counts identify which expression to narrow. Only usable on the lab's hardware if Xcode shows it for Apple9 too.)
- M5 doubles FP16 and 'complex ALU' (transcendental) rate over M4, adds up to 30% more memory bandwidth, and uses second-generation dynamic caching with lower register access latency. (source: https://developer.apple.com/videos/play/tech-talks/111431/ at 2:44 and 3:17; confidence: official; gpu_families: Apple10; openmm_use: nonbonded (erfc, exp, rsqrt in PME direct space and GBSA Born terms). On M5 the complex-ALU bound kernels gain the most; on M3 Ultra they stay as they are, so any benchmark comparison across the two must not credit code changes for this.)
- Global (device) atomics resolve in the GPU last-level cache and became a primary bottleneck on M1 Pro and Max. Apple's pattern is a SIMD prefix sum or reduction, then a threadgroup atomic, then one device atomic per threadgroup, which also spreads the device atomics in time. (source: https://developer.apple.com/videos/play/tech-talks/10580/ at 16:06-16:17; https://developer.apple.com/videos/play/wwdc2022/10159/ at 14:07-16:29; https://developer.apple.com/videos/play/wwdc2020/10603/ (GPU LLC section); confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: force accumulation. Every tile writes 64-bit fixed-point forces through pairs of 32-bit device atomics. Reducing within the SIMD group first (the tile already sums per atom in registers) and emitting one atomic per atom per tile is the Apple-endorsed shape. Also applies to findBlocksWithInteractions' interaction-count atomics and computeRange's counter.)
- A14 (Apple7) redesigned threadgroup memory and made threadgroup atomics much faster, and added SIMD reductions: simd_sum, simd_product, simd_min, simd_max, and bitwise and/or/xor. (source: https://developer.apple.com/videos/play/tech-talks/10858/ at 1:27 and 16:31-22:55; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: neighbor list computeRange (250 us per step on apoa1ljpme). reduceMinMax in sort.metal is a threadgroup-memory tree with one __syncthreads per level. simd_min/simd_max plus one threadgroup step replaces log2(64) barriers with one. Same fix for any tree reduction in bonded or energy sums.)

### Corrections to the brief

1. The task prompt labels Apple10 as "M4 or later". The May 21, 2026 Feature Set Tables put M4 and A18 in Apple9 and only M5 and A19 in Apple10. Any lever gated on supportsFamily(Apple9) covers M3 and M4; gating on Apple10 excludes M4.

2. The brief quotes Apple's 1K to 2K threads per core rule (WWDC22 10159) but does not check it against the platform. MetalContext.cpp:158,172 gives 12 blocks x 64 threads = 768 threads per core on every GPU. That is below Apple's floor, and raising numThreadBlocksPerComputeUnit is a one-line A/B the brief does not list.

3. The brief treats threadgroup staging as neutral or helpful. Apple's M3 shader best-practices talk (111373 at 11:43-12:46) says that on Apple9, threadgroup memory used as a software cache of device data may be slower than reading the buffer directly. sortShortList2 matches that pattern exactly.

4. The brief does not note that every buffer is hazard-tracked. MetalArray.cpp:55 allocates shared buffers with no untracked flag, and Apple's resource-synchronization page says device resources default to tracked. Tracking may add serialization between the PME queue and the main queue that the platform's own events already cover. Tracked-mode behavior across two queues is not documented, so this is a risk to test, not a proven cost.

5. The brief's float-atomics inference for M2 via CAS fits the tables, which list floating-point atomics from Apple7. The M2 float-atomics slowdown is therefore a performance finding, not a missing feature.

6. The brief lists no pipeline descriptor settings. The platform passes no MTLComputePipelineDescriptor (MetalContext.cpp:505), so threadGroupSizeIsMultipleOfThreadExecutionWidth stays false and maxTotalThreadsPerThreadgroup stays 0. Apple documents both as optimization inputs.

7. The __syncthreads macro fences device memory on every barrier (common.metal:14). The brief does not flag this.

- MLX encodes every kernel into a compute encoder created with MTL::DispatchTypeConcurrent and inserts memoryBarrier(MTL::BarrierScopeBuffers) only when a dispatch reads a buffer written, or writes a buffer read, since the last barrier. OpenMM Metal opens a serial encoder (computeCommandEncoder() with no argument), so every dispatch waits on the one before it, even when the two are independent. (source: mlx/backend/metal/device.cpp:335-500 (set_input_array, set_output_array, maybeInsertBarrier) and 575-583 (get_command_encoder); hipdelta-gbsa/platforms/metal/src/MetalQueue.cpp computeCommandEncoder(); confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Per-step orchestration. (source: hipdelta-gbsa/platforms/metal/src/MetalSort.cpp:57-68 and 119; platforms/hip/src/HipSort.cpp:66; platforms/common/src/CommonCalcNonbondedForce.cpp:464, 979, 1049; confidence: inferred; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: PME atom sort. Four fixes, cheapest first. (c) Skip the reduction, because the key is the grid index and its range is already known as [0, gx*gy*gz). (b) An MLX-style two-pass all-reduce using simd_min and simd_max. (a) A multi-block launch as in HIP, with coherent(device) on range[]. (d) Replace the five-dispatch bucket sort with a counting sort over grid cells, since spreading only needs locality.)
- MLX's all-reduce runs inputs up to 4 x 1024 elements in a single threadgroup. Larger inputs run as two passes: a first pass over 32 x 4 rows (1024 x 4 when the input is over 64 MB), then a single-threadgroup second pass of 32 threads. Each threadgroup reduces with simd_reduce, then through threadgroup memory, then with simd_reduce again. MLX never uses a single-pass last-block design. (source: mlx/backend/metal/reduce.cpp:330-405; kernels/reduction/reduce_all.h; confidence: official; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: computeRange and the other global reductions: energy sums, the kinetic energy sum, the max-displacement check. The two-pass design needs no coherence qualifier and no atomic counter. It costs one extra dispatch, which the concurrent encoder makes nearly free.)
- The neighbor-list block sort key in computeSortKeys is (bin << BIN_SHIFT) + blockIndex with 20 bins. The key is unique, so the 'sort' is really a stable 20-way partition. For up to 1024 blocks, MetalSort runs sortShortList2, an O(n^2) rank count where each thread compares its key against every key in threadgroup memory. That is 64-thread groups at about n/64 threadgroups, followed by a blit copyTo. The lab measured it at about 48.5 us per step. (source: hipdelta-gbsa/platforms/metal/src/kernels/findInteractingBlocks.metal:126-141; kernels/sort.metal:53-71; MetalSort.cpp:106-107; MetalNonbondedUtilities.cpp:41-52 and 280; confidence: inferred; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: findBlocksWithInteractions sort. Replace it with a single-threadgroup stable counting sort. For each of the 20 bins, simd_ballot gives each lane's rank inside its simdgroup by popcount, per-simdgroup counts go through a scan in threadgroup memory, and each thread then scatters into a ping-pong output buffer. One dispatch, O(n), with no copy. For more than 1024 blocks (apoa1 2882, cellulose about 12.8k, stmv about 33k), loop that threadgroup over chunks or run a two-pass multi-threadgroup counting sort in place of the uniform=false bucket path.)

(source: hipdelta-gbsa/platforms/metal/src/MetalNonbondedUtilities.cpp:416-423; kernels/findInteractingBlocks.metal:123, 146-203, 306; confidence: inferred; gpu_families: Apple7, Apple8, Apple9, Apple10; openmm_use: Neighbor-list step cost. - MLX's contiguous scan uses one threadgroup per row, with up to 1024 threads each reading 4 elements (2 for 8-byte types). - MSL has no 64-bit simd shuffles, but MLX adds overloads for simd_shuffle, simd_shuffle_down, simd_shuffle_up and simd_shuffle_and_fill_up on uint64_t, int64_t and complex64 that bit-cast to uint2 and shuffle that. ### Corrections to the brief

1. SIMD functions and long: the brief treats SIMD shuffles as unavailable for 64-bit types. MLX shuffles 64-bit values by bit-casting them to uint2 (kernels/utils.h:383-449), which the spec allows. 64-bit simdgroup pre-reduction is therefore possible through shuffles. Only simd_sum and the other reductions lack 64-bit forms.
2. Last-threadgroup reduction lever: MSL 4.1 section 4.8 gives device memory only threadgroup coherence by default. The partial results buffer must be declared coherent(device) (MSL 3.2 and later) or written with atomics, or the last threadgroup can read stale partials. The brief does not say this. MLX avoids the issue by running two-pass reductions.
3. computeRange: the brief misses the root cause of the 250 us cost. MetalSort.cpp:65 hard-codes rangeKernelBlocks = 1, while HIP launches ceil(n / 256) blocks. The range is also known in advance for the PME sort, so the reduction can be skipped entirely.
4. Cross-queue sync: the brief uses events for the PME second queue. Apple documents that MTLFence works across queues on the same device since Metal 3, so sync can happen inside encoders as long as the producer command buffer is committed first.
5. Residency sets: the brief expects little gain. MLX uses them to keep memory resident, not for dispatch speed, so the brief's conclusion stands for speed. The stated reason should change.
6. Blit copies: the brief's orchestration section does not list MetalArray::copyTo's blit encoder switch inside the sort short-list path, which runs every step. MLX shows that one concurrent compute encoder with compute-kernel copies is the production pattern.
7. Neighbor-list sort cadence: the block sort runs every step even on steps that reuse the list, because the rebuild flag is computed after the sort in sortBoxData.
8. The brief's open question on memoryBarrier(resources:) scope is still open. Apple's docs don't say whether that barrier is limited to the listed resources, and MLX sidesteps it by using memoryBarrier(scope: buffers) only.

### Gaps

Apple publishes no GPU driver, AGX firmware or shader compiler source. The low-level ISA and scheduler facts live in reverse-engineered projects (Asahi Linux, dougallj/applegpu, philipturner/metal-benchmarks), which are outside this source family and were not reviewed here. The Metal backend of MLX has no radix sort, so there is no Apple reference for a GPU radix sort. Unverified: whether tracked buffers inside a concurrent encoder make the driver insert implicit barriers (MLX uses untracked buffers throughout, so its code does not answer this), and whether memoryBarrier(resources:) is narrower than a scope barrier. I did not read Apple's compute sample projects in depth or the metal-cpp headers beyond the pipeline descriptor. Nothing here was measured: every cost claim for OpenMM kernels (the 250 us computeRange, 48.5 us sortShortList2) comes from the lab's earlier numbers, and the proposed fixes need benchmarks on the Studio and mini. The M3 Ultra architecture string 'applegpu_g15d' is inferred from MLX's parsing code, not read from the device. MLX fast synch depends on an undocumented memory scope and was not tested.

### Findings

- Mesa's AGX compiler encodes the per-core occupancy table as half-registers against max threads: 104 half-regs (52 full 32-bit registers) gives 1024 threads, 128 gives 832, 160 gives 640, 208 gives 512, and 256 half-regs (128 registers, the ISA maximum) gives 384. AGX_NUM_REGS is 256 half-regs. 104 x 1024 x 2 B is 208 KB, which matches the brief's 208 KB register file. (source: mesa src/asahi/compiler/agx_performance.c:16-19 at e3a986f0; confidence: reverse-engineered; gpu_families: Apple7 (G13), Apple8 (G14); openmm_use: Nonbonded and GBSA pair-tile kernels: on M1 and M2 a tile kernel must stay at or below 52 live 32-bit registers per thread to keep full 1024-thread occupancy. Every 8 half-registers above that costs roughly 64 to 128 threads.)
- Eric Fink measured the same cliff through Metal: on M1 Max a kernel with an unused branch that needs 128 registers drops maxTotalThreadsPerThreadgroup from 1024 to 384 and runs about 20% slower. On A17 Pro all variants keep 1024 threads with no slowdown. The 384 figure matches Mesa's 256 half-reg row exactly, so the M1 table and Apple's compiler agree. (source: RealWorldTech thread 214917, post 214929, Nov 2 2023; confidence: measured-by-third-party; gpu_families: Apple7 shows the cliff; Apple9 (A17 Pro, so M3 and M4) does not; openmm_use: Nonbonded and GBSA tiles with rare heavy paths, such as exclusion handling, PME exclusion corrections or GBSA second-pass branches: on the M3 Ultra a cold branch no longer sets occupancy, so splitting it into a separate kernel buys little. On M1 and M2 it still matters.)
- Apple says that from Apple9 the register file is a cache and registers are allocated and freed during the SIMD-group's lifetime. Threadgroup, tile, stack and buffer data share fewer, larger on-chip caches. The shader core monitors use and lowers occupancy to prevent spills, so 'your shader's occupancy will be impacted by how your shaders access threadgroup, tile, stack, and buffer memory in addition to its dynamic register usage.' (source: Apple tech talk 111375, transcript; confidence: official; gpu_families: Apple9 (M3, M4) and later; openmm_use: findBlocksWithInteractions declares workgroupBuffer[256*warpsPerBlock] ints (findInteractingBlocks.metal:325), which is 1 KB per SIMD-group. The sort bitonic stages also use threadgroup arrays. On the M3 Ultra these now compete with registers for the same storage, so shrinking threadgroup arrays can raise occupancy even when registers are not the limit. Measure with Xcode's occupancy counters, not the M1 table.)
- Apple says FP16, FP32 and integer instructions run on separate ALU pipelines on Apple9, with up to 2x ALU throughput over earlier GPUs, but only when instructions come from multiple SIMD-groups, so the gain depends on occupancy. (source: Apple tech talk 111375, transcript; confidence: official; gpu_families: Apple9 and later; openmm_use: Nonbonded and GBSA inner loops mix FP32 math with integer exclusion-bit and index work. The dual-issue gain appears only if occupancy stays high, so a register-heavy tile kernel loses twice on M3.)
- leman's M3 and A17 Pro tests: FP32 and FP16 co-issue perfectly, so aggregate throughput is the sum. FP plus INT co-issue has a penalty, 'maybe only every third INT'. An FP32+FP16+INT mix lands near the average of the two. (source: TechBoards M3 thread page 34, post by leman, Nov 23 2023; confidence: measured-by-third-party; gpu_families: Apple9; openmm_use: Nonbonded, GBSA and PME interpolate: FP16 for low-precision terms is free extra throughput on M3, but integer index and bit math next to FP32 serializes partly. ### Corrections to the brief

The brief's GPU family labels are off for M4. Apple's May 21, 2026 feature set tables put M3 and M4 both in Apple9 and M5 in Apple10, so M4 numbers such as Rigel's and the M4 Pro cache paper belong with the M3 Ultra, not with a separate Apple10 bucket.

The brief's M1 and M2 per-core figures (208 KB registers, 384 to 3072 threads, 24 SIMDs per core) do not carry over to the M3 Ultra as occupancy limits. Two things show this. Apple tech talk 111375 says the Apple9 register file is a cache, and threadgroup, stack and buffer memory share one on-chip pool. Eric Fink measured 1024 threads on A17 Pro where M1 Max drops to 384 for the same kernel. Mesa's occupancy table caps at 1024 threads per core at 52 or fewer registers, which disagrees with the brief's 3072 maximum. Turner's CommandConcurrency comments estimate 351 to 378 KB of M1 Max register file, against the README's 208 KB. Treat per-core register size and maximum threads as unsettled, and on the M3 Ultra measure occupancy in Xcode instead.

The brief's "about 60 KB shared memory per core" is Turner's per-core estimate. The official limit is 32 KB per threadgroup on every family from Apple4 to Apple10. Mesa and Honeykrisp expose 32 KB, though lib/agx_usc.h defaults bytes_per_threadgroup to 65536. On Apple9, threadgroup memory also competes with registers.

Float atomics are listed from Apple7, but the G13 ISA has no float atomic opcode and Mesa lowers atomics to integer ops and cmpxchg. On M1 and M2 they are CAS loops. That is the likely cause of the M2 190.8 ms result, not just contention. The Apple9 native path stays inferred from the lab's own timing.

The second-queue overlap lever needs a cap. Turner measured that separate queues give only 2x concurrency, that full concurrency (up to 96 commands) happens only inside one encoder, and that buffers from one MTLHeap block cross-encoder overlap.

The worktree's __syncthreads carries mem_device on every barrier. The brief treats barriers as threadgroup-only.

M2 already had a non-returning 64-bit atomic min/max in hardware, per metal-benchmarks, before the API exposed 64-bit atomics on Apple9. No Apple GPU has a 64-bit atomic add.

### Gaps

No public reverse engineering of the M3 or M4 ISA (G15/G16) exists. applegpu, Asahi docs and Mesa stop at G13 and G14, so every opcode, latency and occupancy number above is M1 or M2 unless it is marked as Apple or third-party Apple9 data. Dual issue on Apple9 rests on Apple's tech talk, one forum tester and applegpuinfo's model.

No one has published threadgroup memory bank count, bank width or conflict penalties for any Apple GPU.

No per-type, per-address-space atomic throughput table exists for Apple9: float add, 32-bit int add, threadgroup against device, contended against uncontended. Nor is there anything on the cost of cross-die atomics on Ultra parts.

L1 and L2 sizes and latencies for M3 and M4 GPUs are unmeasured in anything I found. The chipsandcheese M2 Pro article, which gives an 8 KB L1, a 3 MB L2 and 234 ns SLC latency in its search snippet, was not fetched and read. No source measures the cost of mem_device on threadgroup_barrier.

I did not read these:
- Philip Turner's molecular-renderer and MM4 docs (cloned, unread).
- The arXiv papers 2501.14925, 2608.09075 and 2504.13385 (downloaded, unread).
- Upstream openmm PRs #4346 and #4348.
- The worktree's nonbonded and GBSA tile kernels. So the per-lane-index shuffle concern in the shuffle finding is unconfirmed.

The M3 Ultra-specific numbers are extrapolations from other Apple9 parts: about 21 TFLOPS FP32, about 650 to 740 GB/s achievable bandwidth, and about 15,000 threads to fill the GPU.

### Corrections to the brief

1. The brief treats counter tooling as Xcode-bound and unverified. macOS 27 ships /usr/bin/gpucapture and /usr/bin/gpudebug, and gpudebug `profile run` gives headless per-shader cost and counter JSON on M3 and later. This is the answer to "can the shader profiler run headless". Whether it goes down to per-line cost is still unverified.

2. The brief's open question about counter sample buffers returning zeros (wgpu #9414) now has an Apple answer. Apple's doc says Apple silicon samples only at stage boundaries, and the MTL4 counter heap is timestamp-only. Zeros for per-dispatch StageUtilization or Statistic samples are expected behavior, not a bug. The brief's timestamp approach stays correct.

3. Lever 4 in the brief (an MSL 4.1 acquire/release "last threadgroup reduces" pattern) is incomplete. Per MSL 4.1 section 4.8, device memory is only threadgroup-coherent by default. The partials buffer must also be declared coherent(device) (Metal 3.2 and later) for cross-threadgroup visibility to be guaranteed. The same gap applies today to computeRange and any kernel using __threadfence from common.metal:15.

4. The 256-thread VkFFT Metal cap that the brief cites from arXiv 2603.27569 is confirmed in code. See vendored vkFFT.h 1.2.33 around line 39866, unchanged at upstream 066a17c. The code comment ties it to DCT-IV, so R2C transforms could lift it. The brief also does not mention that VkFFT compiles its kernels with fast math enabled.

5. The brief does not mention that the compiler hints [[max_total_threads_per_threadgroup]] and -fmax-total-threads-per-threadgroup exist from Metal 3, or MTLCompileOptions.maxTotalThreadsPerThreadgroup (macOS 13.3). 6. Computing per-step costs: computeRange's 250 us on apoa1ljpme follows from rangeKernelBlocks = 1. It is a one-threadgroup kernel, not a memory-bound one. The brief does not identify this.

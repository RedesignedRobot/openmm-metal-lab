# API check of the native Metal design study

The research lane checked every API named in research/2026-09-25-metal-native-design.md against Apple's documentation and the metal-cpp headers vendored at 6df2b8bcb (libraries/metal-cpp/Metal), on 2026-09-24 at about 21:50Z.

API check of the native Metal study, against Apple's docs and the vendored metal-cpp at 6df2b8bcb (libraries/metal-cpp/Metal): every API the designs name exists with the claimed shape. There are 3 undocumented behaviors to probe, 1 version gate, and 2 citation fixes. Details:

Undocumented, so probe before relying on them
1. Zero-threadgroup indirect dispatch. dispatchThreadgroups(indirectBuffer:...) (macOS 10.11, MTLComputeCommandEncoder.hpp:68), the MTLDispatchThreadgroupsIndirectArguments page and the direct dispatchThreadgroups page are all silent on {0,1,1}. The study already says so. Keep early exits until a probe shows zero is safe on both chips.
2. How a tracked command counts as a writer. Apple says tracking acts "when at least one command writes to a tracked resource" (MTLHazardTrackingMode.tracked), but never says how it decides that for a directly bound buffer. Reflection exposes BindingAccessReadOnly, ReadWrite and WriteOnly (MTLArgument.hpp:76-79), and every posq parameter in the Metal kernels, pme.cc and gbsaObc.cc is const. If the driver treats every bound buffer as written, P and D serialize on posq and charges however the passes are split. That's a second possible cause for a flat arm B, next to encoder merging. If B and B-s both come back flat, that's the next suspect.
3. The scope of memoryBarrier(resources:). The doc only says barriers "ensure the relevant passes finish updating resources before starting the stages of subsequent commands that depend on those resources" (macOS 10.14, hpp:77-78). That's moot now that the concurrent encoder is stopped.

Version gate
4. Per-operation memory_order_acquire, release and acq_rel are MSL 4.1 and later (MSL 6.16.1), and the platform compiles at LanguageVersion3_2 (MetalContext.cpp:483). The fused integrator's CM-fold extension ("last-threadgroup reduction, acquire/release") would need the 4.1 bump the review keeps out. It doesn't have to wait for it, though: atomic_thread_fence with memory_order_seq_cst and thread_scope_device is available from MSL 3.2 on Apple silicon (6.16.1, 6.16.2, 6.16.3). Relaxed counters plus that fence build the same pattern at 3.2. Threadgroup atomic_float add is also 4.1 only (6.16.4.5); device atomic_float is Metal 3.

Verified as the study states
5. Events: encodeSignalEvent (MTLCommandBuffer.hpp:156) is legal "only between passes" and fires "after the GPU finishes the buffer's prior commands". signaledValue (MTLEvent.hpp:72) is macOS 10.14, and waitUntilSignaledValue (:73) is macOS 12. onebuf's in-buffer signal is legal because MetalQueue ends the encoder at signals.
6. Queue backpressure: newCommandQueue() allows "up to 64 uncompleted command buffers" (MTLDevice.hpp:421, with the explicit-count form at :422). makeCommandBuffer "blocks the calling CPU thread when the queue doesn't have any free command buffers". The command buffers keep strong references, and MetalQueue.cpp:57 uses commandBuffer(), the retained form. So the study's "resize during run-ahead is safe" holds for buffer lifetime.
7. Storage and tracking: MTLStorageMode.shared is the default on Apple silicon, and the doc makes the app responsible for CPU/GPU ordering on shared memory. That's why the wait-free ring must read only completed slots, and the study already says so. Resources from an MTLDevice default to tracked. Automatic synchronization covers only an MTLCommandQueue and directly bound resources, and an MTL4CommandQueue gets no hazard tracking at all. ResourceHazardTrackingModeUntracked = 0x100 is at MTLResource.hpp:84.
8. MTLFence "orders memory operations between GPU passes". MTLDispatchType.concurrent makes the app "responsible for synchronizing" shared resources (computeCommandEncoder(DispatchType) at MTLCommandBuffer.hpp:152, setDispatchType at MTLComputePass.hpp:77).
9. ICBs: MTLIndirectComputeCommand has setKernelBuffer, setThreadgroupMemoryLength, concurrentDispatchThreadgroups and setBarrier, and no setBytes (doc topics; MTLIndirectCommandEncoder.hpp:89-102). Its only dispatch is concurrent, with explicit barriers, which adds to the rejection. executeCommandsInBuffer with an indirect range is at hpp:74-75.
10. Device queries: supportsFamily (MTLDevice.hpp:558), with GPUFamilyApple8 = 1008 and Apple9 = 1009 (:183-184). Also present: recommendedMaxWorkingSetSize (:529, "an approximation of how much memory ... without affecting its runtime performance"), maxBufferLength (:383) and maxThreadgroupMemoryLength (:385).
11. The counter sampling for arm B-s is in the vendored headers: newCounterSampleBuffer (MTLDevice.hpp:439), supportsCounterSampling (:554), CounterSamplingPointAtStageBoundary (:221), ComputePassSampleBufferAttachmentDescriptor setSampleBuffer and setStartOfEncoderSampleIndex (MTLComputePass.hpp:36-51), and computeCommandEncoder(ComputePassDescriptor*) (MTLCommandBuffer.hpp:150).
12. MSL: simd_shuffle_rotate_down, ballot, shuffle, any, max, sum and prefix_exclusive_sum are in 6.10.2. Function constants are 5.8.1. atomic_fetch_max on atomic_uint is 6.16.4.5 (Table 6.27). atomic_ulong gets min and max only, relaxed only, in 6.16.4.6.
13. Feature Set Tables: memory barriers Apple3, indirect dispatch Apple3, SIMD permute Apple6, SIMD reduction Apple7, float atomics Apple7, 64-bit atomics Apple9, ray tracing in compute Apple6, 32 KB threadgroup memory, 31 buffer-table entries per kernel (so the bonded design's 31-buffer limit is right), 1024 threads per threadgroup.
14. Fast math error bounds for my GBSA kill test (MSL Table 8.2): fast rsqrt <= 2 ulp, 1.0/x <= 1 ulp, x/y <= 2.5 ulp, fast exp <= 3 + floor(|2x|) ulp. precise sqrt is correctly rounded (Table 8.1). Replacing precise sqrt and fast reciprocals with one rsqrt moves Gpol by a few ulp, about 1e-6 relative. That's far under the 2.5e-5 gate.

Conflicts and citation fixes
15. Feature Set Tables footnote 7 says "The full set of 64-bit atomic operations is supported on all platforms starting with Apple9." MSL 6.16.4.6 lists only min and max for atomic_ulong, and the atomics lane's compile test failed on add. Trust the spec plus the compiler.
16. The study cites "MSL 4.1 1.6.3" for fast rsqrt, divide and exp. Section 1.6.3 covers the compiler options. The fast:: functions are in 6.6, and their error bounds are in Table 8.2 (section 8.4).
17. The Dynamic Caching and ALU quotes come from Apple's tech talk 111375, and the "1K to 2K threads per core" and concurrent-dispatch quotes from WWDC22 10159. The brief carries those; I didn't re-fetch them tonight.

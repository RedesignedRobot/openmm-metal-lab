A native Metal platform for OpenMM on Apple silicon

Amir Ayub, using Claude Fable 5.1

Independent work · @RedesignedRobot

Code · Data and harnesses · Discussion, openmm#5397

Abstract

OpenMM, the molecular dynamics engine behind Folding@home's GPU cores, runs on CUDA, HIP and OpenCL but not on Metal. Apple's OpenCL can't run the mixed precision Folding@home uses, because Apple GPUs have no 64-bit floating-point hardware. We built a native Metal platform the way OpenMM's CUDA and HIP platforms are built: a thin compute context on Common Compute, so every shared GPU kernel compiles unchanged. Kernels encode into one open command buffer, and mixed precision uses double-float arithmetic. On an M2, an M3 Pro and an M3 Ultra, the platform passes 107 to 109 of 110 tests, most of them ported from OpenMM's OpenCL suite, and its only repeatable failure also occurs with OpenCL on unmodified OpenMM on M3 GPUs. In single precision it matches OpenCL on OpenMM's benchmark suite, at 0.99 to 1.07 times its speed, and leads by 20 to 28% on the one Folding@home work unit that uses the CCMA constraint solver, for reasons not yet isolated. Mixed precision, which OpenCL can't offer on these GPUs, costs 15 to 42% against Metal's single precision and runs 2.8 to 11 times faster than the CPU in the same machine. Force errors against OpenMM's double-precision Reference platform match OpenCL's on every chip. Standalone Metal-native kernels run the neighbor-list block search a further 2.3 to 3.1 times faster, and are not yet part of the platform.

IntroductionCapable GPUs, outside the science.

Folding@home simulates protein dynamics on volunteers' computers, and most of its throughput comes from GPUs running OpenMM1,2. Every Mac with Apple silicon has a capable GPU with unified memory, but a Mac that joins Folding@home today contributes through its CPU alone.

Three things stand in the way. OpenMM has no Metal platform. Apple's OpenCL, deprecated since 2018, runs only OpenMM's single precision. And the Folding@home client can't yet detect a GPU that isn't on PCI8. This report addresses the first two.

We describe the platform's design, then measure it at three levels: individual kernels against OpenCL, the whole platform on Folding@home's benchmark work units and on OpenMM's benchmark suite, and OpenMM's own test suite. The platform ran on three Apple chips spanning 10 to 60 GPU cores, and the kernel studies on two or three of them.

ResultsA thin platform on Common Compute.

All 26 real GPU programs we captured from OpenMM compile as Metal Shading Language and build every compute pipeline state, on the M2 and the M3 Ultra. Two language gaps shaped the design. Program-scope thread builtins, which let the common kernels read their thread index without changing signatures, need MSL 3.1. MSL has no erf or erfc, so the platform supplies its own. The common kernels needed only an address-space macro, PRIVATE, which is empty on the other platforms, and a few explicit (mixed) literals.

One open command buffer per step

Metal has no direct equivalent of a CUDA stream or an OpenCL queue. Work is encoded into command buffers, and nothing runs until a buffer is committed. Committing one buffer per kernel costs 23.6 µs of host time per dispatch on the M2 and 15.1 µs on the M3 Ultra. Encoding into one open buffer costs 0.12 and 0.11 µs, less than OpenCL's 0.38 to 0.39 µs. So the platform keeps one buffer open and commits it only when the host needs a result. A step then takes 1.01 command buffers without a cutoff and 2.01 with PME, a bound that a new test, TestMetalCommandBatching, enforces.

Mixed precision without 64-bit hardware

OpenMM's mixed precision computes forces in single precision and integrates positions and velocities in double. The Metal platform represents each double as an unevaluated sum of two floats, a technique that goes back to Dekker3. Values stay IEEE doubles in device memory, so host code and array layouts match the other platforms. Kernels split them on load and rejoin them on store.

Every double-float operation with a proven error bound stays within it. The largest error, for division, is 6.80 units of 2−48 against a bound of 15. One Verlet step agrees with CPU double to 1.08e-14 in velocity, where float gives 1.01e-7. Over one step of a variable-step integrator with a closed-form answer, the platform matches double to 6.7e-15 in position. Applying a transcendental function to a mixed value is a compile error that names the function and the line, never a silent fall back to float.

Agreement depends on the math mode. With Metal's fast math, asin matches OpenCL bit for bit on only 43% of inputs. In safe mode with precise functions, sqrt, rsqrt, reciprocal, divide, fma, asin, acos and normalize match on 100%. The platform compiles in safe mode with precise functions. At startup it switches reciprocal square root, reciprocal, exp and log to their fast versions, each only if its error is below 1e-6.

Close to OpenCL, well ahead where CCMA runs

We ran FAHBench's three work units5 on each chip: dhfr in implicit solvent (2,489 atoms), dhfr with PME (23,558) and nav with PME (173,112). Each configuration ran three rounds of 60 s after 200 warm-up steps, in rotated order. Metal is 1 to 4% ahead of OpenCL on dhfr-implicit and nav, a small margin but outside the round-to-round spread, and 20 to 28% ahead on dhfr with PME. That work unit constrains every bond and every H–X–H angle, so all 3,072 of its non-water constraints go to the CCMA solver. The other two constrain only bonds to hydrogen, which OpenMM handles with SETTLE and SHAKE clusters, and send nothing to CCMA. We have not yet isolated whether CCMA is the cause.

OpenMM's benchmark suite

We also ran OpenMM's own benchmark.py, unmodified, on each chip: nine systems from 2,489 to 1,067,095 atoms, all with a 4 fs step and only bonds to hydrogen constrained, so none of them uses CCMA. Each configuration ran once, for 60 s. In single precision, Metal runs at 0.99 to 1.07 times OpenCL's speed on every system and chip. Mixed precision, Folding@home's, runs at 0.58 to 0.89 times OpenCL single, and 4.0 to 11 times the CPU. The cost is 28 to 42% on the three 23,558-atom dhfr systems and 15 to 23% on the two largest. We have not yet measured where it goes.

Scaling with system size

To see how each GPU fills, we ran TIP3P water boxes from about 2,700 to 792,000 atoms. Throughput in atom·ns/day climbs until the GPU saturates, then levels off. The M2 and M3 Pro deliver the same work per GPU core at the plateau. The M3 Ultra plateaus at 11.7 million atom·ns/day, but at two thirds of the smaller chips' rate per core. OpenCL plateaus within 5% of Metal.

Accuracy against the Reference platform

We compared forces from each GPU platform with OpenMM's Reference platform, which computes in double precision on the CPU, from the same positions. Metal's errors are identical on all three chips: 1.21e-6 on dhfr and 1.75e-6 on nav, where OpenCL gives 1.80e-6 to 1.82e-6. In 0.1 ns of constant-energy dynamics, Metal drifts no more than the CPU platform does, and the CPU alone spans −53 to −160 kJ/mol/ns across the three machines. Runs this short measure the protocol rather than the platform, so they are not comparable with OpenMM's published drift figures, which come from longer runs with tighter constraints.

OpenMM's test suite

We ported OpenMM's OpenCL tests to Metal and added two of our own, for command-buffer batching and mixed precision: 55 test programs, each run in single and mixed precision, for 110 tests.

The only repeatable failure is testLargeForces in the energy minimizer tests. On both M3 chips it fails the same way with OpenCL on unmodified OpenMM, and it passes on the M2. The Reference and CPU platforms pass it. It is an existing issue in OpenMM on M3 GPUs, not in the Metal platform. The other failures are statistical tests that pass on rerun.

Headroom: Metal-native kernels

Every result above uses OpenMM's common kernels unchanged. Separately, we rewrote two of the most expensive kernels in native Metal, using SIMD-group operations that OpenCL on Apple GPUs doesn't expose. The neighbor-list block search, rewritten with simd_ballot, is 2.3 to 3.1 times faster than OpenCL and finds identical interaction sets. The native nonbonded kernel is 1.68 times faster on the M3 Ultra, but 8 to 11% slower on the M2, where its exclusion handling costs about 0.46 ms against OpenCL's 0.17 ms. The OpenCL baseline in that harness uses a fixed launch size, so we treat the M3 Ultra result as provisional.

DiscussionA first step, with a clear next one.

A Metal platform built like CUDA and HIP runs OpenMM on Apple GPUs with the accuracy of an established platform, and it matches OpenCL's speed in single precision on OpenMM's benchmark suite. It also delivers the mixed precision Folding@home requires, which OpenCL can't on this hardware, at a cost of 15 to 42% in speed. The one clear lead over OpenCL, on the work unit that uses CCMA, is not yet explained. The larger gains measured in native kernels are the route past OpenCL, and they would live inside the platform, leaving the common kernels untouched.

Several limitations apply.

  • Mixed-precision minimization is slow. Without 64-bit atomics, its reductions run in a single threadgroup and take 80% of the time. On nav on the M2, it takes 264 s, against 58 s in single precision and 300 s on the CPU.
  • Coverage. Three chips, all on macOS 27. No M1 or M4 hardware. The benchmark suite ran once per configuration, and without its AMOEBA tests, because the platform has no AMOEBA plugin.
  • Conditions. The M3 Pro and M3 Ultra were in everyday use during the runs. Between rounds, dhfr timings on those chips vary by up to 9%, and the M3 Ultra's CPU timings by up to 16%.
  • Scope. One device per context, no double precision, and QTBIntegrator in single precision only.

The approach follows recent work in which Claude optimized open-source biomolecular models under scientific supervision, checking every change against the unmodified code9. Here the target is molecular dynamics, and the hardware is the Macs many scientists already own.

MethodsHow we measured.

BuildCommit f9347f6c5, built from clean on each machine: from a git archive with a matching source manifest on the M3 Pro and M3 Ultra, and as an independent verification build on the M2. Apple clang 21.0.0, macOS SDK 27.0, Release.
MachinesMac mini, M2, 8 CPU and 10 GPU cores, 8 GB. MacBook Pro, M3 Pro, 12 CPU and 18 GPU cores, 36 GB. Mac Studio, M3 Ultra, 28 CPU and 60 GPU cores, 96 GB. All on macOS 27.0.
ClocksPlatform throughput and minimization: host wall clock (time.perf_counter) over whole steps. Benchmark suite: benchmark.py's own host wall clock (datetime.now) over whole steps. Standalone kernels: GPU timestamps. Dispatch cost: host clock. We never compare numbers from different clocks directly.
ProtocolThree rounds per configuration, order rotated each round, 200 warm-up steps, 60 s timed, at nice 0. Scaling: one 30 s run per box size. Benchmark suite: benchmark.py defaults, one 60 s run per configuration in a separate process, order rotated from test to test.
AccuracyForces compared with the Reference platform from the same positions. Drift from 0.1 ns of constant-energy dynamics on dhfr, as the fitted slope of total energy.
ConditionsThe M3 Pro ran its first round on battery and the rest on AC. The M3 Ultra ran alongside a dictation app and two virtual machines.

One caveat: the absolute times Apple's OpenCL layer reports look like mach ticks and not nanoseconds (the sum is about 0.15 ms per step against 4.9 ms of wall time), so I only trust the fractions.

**Is MSL close enough to share the Common kernels?** I tried it. A macro prelude plus one mechanical signature rewrite, kernel files byte-identical to master, compiled at runtime with `newLibraryWithSource` on macOS 27:

- 49 of the 67 files in `platforms/common/src/kernels` compile with zero errors. That is every file that holds complete kernels.
- The other 18 are the code fragments that the host splices into generated kernels (bondForce.cc, coulombLennardJones.cc, customNonbonded.cc and so on). They cannot compile alone on any platform. The next section tests them spliced the way the host does it.
- What made it work:
  - Current MSL accepts thread position builtins declared at program scope (`uint3 gid [[thread_position_in_grid]];`). `GLOBAL_ID`, `LOCAL_ID`, `GROUP_ID` and the size macros stay parameterless and work from helper functions. I ran this on the M2 and the M3 Ultra and the values are right.
  - Buffer indices are assigned automatically to pointer arguments. Value arguments need rewriting to `constant T&` with a local copy at function entry; that is the one mechanical rewrite.
  - `thread` is a keyword in MSL and a variable name in some kernels, handled with a define.
  - `simd_ballot`, `simd_shuffle`, `simd_shuffle_down` and `simd_shuffle_xor` exist, so the `BALLOT` and `SHFL` paths that the HIP platform uses map directly. The census compiled the Common kernels with those paths switched on.
- What it does not show: compiling is not running. The prelude's `erf` and `erfc` are polynomial stand-ins that need an accuracy check.

**The real program set.** Standalone files are not what the platform compiles, so I patched `OpenCLContext::createProgram` to dump every program of an apoa1rf and an apoa1pme run on the M2 (26 programs, fragments spliced in, including nonbonded.cl, findInteractingBlocks.cl and sort.cl, which live outside Common). With the context defines and common.cl swapped for a Metal prelude and the bodies untouched apart from two regex rewrites, all 26 compile and every kernel in them builds a pipeline state, on the M2 and the M3 Ultra. findBlocksWithInteractions compiles on its `SIMD_WIDTH 32` path, with its 21 barriers mapped to `threadgroup_barrier`. The two rewrites:

1. Kernel value parameters become `constant T&` plus a local copy at entry (338 sites).
2. OpenCL vector literals `(real4) (a, b, c, d)` become `real4(a, b, c, d)` (52 sites). This one matters: MSL is C++, so the OpenCL form compiles without a warning as a cast of a comma expression and yields `float4(d)`. A port that skips this rewrite builds and computes wrong numbers.

**Atomics.** Metal has no 64-bit atomics (`atomic<ulong>` does not build on M2 or M3), but the split-word `atom_add` from common.cl ports directly onto `atomic_uint`. I ran it under heavy contention (2^22 adds into 8 cells, a carry on nearly every add, mixed signs): exact on both chips, 5 ms on the M2. `atomic<float>` fetch_add also builds and gives right sums on the M2, not only on M3 and later, but it is slow there: 2^20 contended adds take 191 ms on the M2 against 0.34 ms on the M3 Ultra, which looks like a compare-exchange loop against a hardware path. So fixed-point accumulation stays the right choice for M1 and M2, and float atomics for gridSpreadCharge look interesting only from M3 on.
